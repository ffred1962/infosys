# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

InfoSys is a small FastAPI demo application (Russian-language UI/docstrings) combining server-rendered Jinja2 pages with a REST API. Python package layout uses plain top-level packages (no `src/` layout), imported as `api.*`, `views.*`, `routers.*`, etc.

Known gaps and deferred follow-ups (deliberately out of scope when they came up) are tracked in [TODO.md](TODO.md) — check it before assuming something wasn't considered.

## Commands

Run all commands from the repo root, using the project venv at `.venv\Scripts\`.

- Run the dev server (with reload): `.venv\Scripts\python.exe -m uvicorn main:app --reload` (also available as the VS Code task "Run FastAPI" and launch config "FastAPI: Uvicorn"). Serves on `127.0.0.1:8000`.
- Run tests: `.venv\Scripts\pytest.exe`
- Run a single test: `.venv\Scripts\pytest.exe tests/test_api_plus.py::test_plus_success`
- Run tests with coverage: `.venv\Scripts\pytest.exe --cov` (an `htmlcov/` report and `.coverage` data file already exist from prior runs)
- Install dependencies: `.venv\Scripts\pip.exe install -r requirements.txt`
- Apply DB migrations: `.venv\Scripts\alembic.exe upgrade head` (run from repo root, since `alembic.ini` uses relative `sqlalchemy.url = sqlite:///data/infosys.db`) — also runs automatically on every app startup now, see `db/migrate.py` below
- Generate a new migration after changing a model: `.venv\Scripts\alembic.exe revision --autogenerate -m "message"`

## Architecture

**Several routing trees are mounted on the same `FastAPI()` app in [main.py](main.py):**
- `api/plus.py` — `APIRouter(prefix="/api")` for public JSON REST endpoints (e.g. `POST /api/plus`), documented via Swagger/Redoc.
- `api/task_status.py`, `api/city.py`, `api/firm_type.py` — three near-identical `APIRouter`s (`prefix="/api/admin/taskstatus"` / `"/api/admin/city"` / `"/api/admin/firmtype"`), each an **admin-gated** JSON REST API (`POST ""`, `PATCH "/{id}"`, `DELETE "/{id}"` for the corresponding lookup table), called via **AJAX (`fetch`) from `js/taskstatus.js`/`js/city.js`/`js/firm_type.js`** rather than from a browser form — see "Task statuses" below, which is the reference implementation the other two copy. Each handler starts with a local `_require_admin(request, session)` call (same pattern as `views/admin/usermgt.py`); all three still show up in `/docs` like any other route (schema disclosure only — every call still re-checks admin access). `task_status.py` additionally pre-checks (plus an `IntegrityError` backstop) that no `Task` references a status before deleting it; `city.py`/`firm_type.py` skip that check since nothing currently has an FK to `city`/`firm_type` — add the same in-use guard there the day something does.
- `api/bug.py` — `APIRouter(prefix="/api/bug")`, **not admin-gated**: `POST ""` is reachable by *any active authenticated user* (via `resolve_authenticated_access`, the same "any logged-in user" helper `/crm` uses) since anyone should be able to file a bug report, not just admins. See "Bug reports & notifications" below for what it does and the admin-only management pages (`api/admin_bug.py`, `api/admin_notification.py`) that consume the same tables.
- `api/task.py` — `APIRouter(prefix="/api/task")`, **ownership-gated, not role-gated**: every route requires *any* authenticated user (`resolve_authenticated_access`), but then further restricts each action to whichever of `Task.author_id`/`Task.assignee_id` actually owns that specific row — see "Tasks" below.
- `api/firm.py` — `APIRouter(prefix="/api/firm")`, any-authenticated-user-gated (`resolve_authenticated_access`, no ownership/role restriction beyond being logged in): `POST /api/firm/search` backs the ПОИСК button on `/crm/firm_finder` — see "Firm finder" below for what it does and `core/firm_search.py` for the actual search implementation.
- `routers/pages.py` — a data-driven table of server-rendered HTML pages. Each page is a `PageRoute(path, handler, name)` tuple registered in the `PAGE_ROUTES` list, and the handler functions live in `views/*.py` (one module per page, including subpackages `views/admin/` and `views/crm/`). Adding a new page means: write a `views/<name>.py` handler that calls `render_page(...)`, add its template under `templates/`, and append a `PageRoute` entry to `PAGE_ROUTES`. Note `PageRoute.name` is just the FastAPI route name (used only if something calls `url_for`, which nothing currently does) — it doesn't have to match the path, but keep it intuitive (e.g. the page at `/proba` is named `"proba_page"`, not `"home_page"`, even though its handler function is still `views/home.py:home_page` — the Python function name and the route name are independent).
- `routers/admin_auth.py` — `APIRouter(prefix="/admin")` with the two POST form actions (`/admin/setup`, `/admin/login`) that back the `/admin` auth flow described below. Kept separate from `routers/pages.py` because that table is GET-only by design. This is also the **shared login endpoint for any authenticated-only page**, not just `/admin` — see "Authentication" below for the `next`-redirect mechanism that makes that work.
- `routers/admin_usermgt.py` — `APIRouter(prefix="/admin/usermgt")` with the POST actions (`toggle-active`, `assign-role`, `remove-role`, `new-role`, all under `/{user_id}/...`) for the user/role management page. The page's own GET route lives in `PAGE_ROUTES` as usual (`views/admin/usermgt.py:usermgt_page`) since it takes no path params; only the mutating actions needed a path param and got pulled into their own router, same reasoning as `admin_auth.py`. Unlike `task_status` (see below), these mutations are still classic form-POST + 303 redirect, not AJAX.

**`/` is a redirect, not a page**: `views/root.py:root_redirect` is a bare `RedirectResponse(url="/crm", status_code=307)` registered as `PageRoute("/", root_redirect, "root_page")` — it does no auth work itself, since `/crm` immediately re-checks via `resolve_authenticated_access` on the request that follows the redirect (see "Authentication for any-logged-in-user pages" below). The original home page (unchanged content/handler/template — `views/home.py:home_page` rendering `templates/index.html`) moved to `/proba` (`PageRoute("/proba", home_page, "proba_page")`); `templates/base.html`'s "Главная" nav link and `templates/404.html`'s "Вернуться на главную" link both point at `/proba` accordingly, not `/`.

**Two templates for the top-level shell**: `templates/base.html` (the original — has the top `<nav>` link bar: Главная/О проекте/Контакты/Калькулятор/Request, and a width-constrained `container` + `col-lg-8` centered column, appropriate for short text/marketing content) is still used by the public pages (`index`, `about`, `contacts`, `calculator`, `request`, `404`). `templates/base1.html` is the admin/CRM shell — no public nav bar (replaced by the topbar described below), and a **full-width `container-fluid` layout** (not the narrow centered column) since data tables need the space; don't reintroduce a `col-lg-*`-constrained wrapper here, and don't let a new admin/CRM template accidentally extend `base.html` instead.
- **Topbar** (`templates/base1.html`, inside an overridable `{% block topbar %}`): hamburger menu icon (`bi-list`, top-left, currently unwired — no handler yet), and three top-right icons — bug-report (`bi-bug`, opens the modal described below), notifications bell (`bi-bell` with a static `0`-count badge, **not yet wired to real unread-notification data**, still a placeholder), and a colored circular avatar showing the first letter of `current_user_email` (falls back to `"U"` if that context var isn't passed — most page handlers don't pass it, only `views/admin/admin_page.py` currently does). `templates/admin/login.html` and `templates/admin/setup.html` override `{% block topbar %}{% endblock %}` to render nothing — there's no logged-in identity to show pre-auth, and `login.html`'s heading was deliberately changed from "Вход в админку" to plain "Вход" once the login page became shared across `/admin` and `/crm`, not admin-specific.
- **Bootstrap JS bundle**: `base1.html` is the only template loading `bootstrap.bundle.min.js` (jsdelivr, real SRI hash computed the same curl+`openssl dgst -sha384` way as the CSS) — added specifically to power the bug-report modal's `bootstrap.Modal` component. `base.html` doesn't load it and doesn't need to, since the public pages have no JS-driven Bootstrap components.

**Two mutation styles coexist on purpose**: form-POST + 303 redirect (setup/login, `usermgt`) vs. JSON API + AJAX (`task_status`). Prefer AJAX (a JSON endpoint under `api/`, called via `fetch` from a page-specific file in `js/`) for pages where individual row actions should update the DOM in place without a full reload; the form-POST pattern is still fine for simple one-shot actions where a redirect back to the same page is an acceptable UX. When adding a JSON API for an admin-gated page, still admin-gate every handler explicitly (there is no shared middleware for this — `/api` is not covered by the session-gating logic the way `/admin*` pages are) and add its path prefix to `middlewares/no_cache.py`'s `NO_CACHE_PATH_PREFIXES` if it serves authenticated data.

**View helper**: `views/base.py:render_page()` is the single place that builds the Jinja2 context (`title`, `active_page`, plus optional `extra_context`) and returns a `TemplateResponse`. All page handlers go through it rather than calling `templates.TemplateResponse` directly. `core/templates.py` holds the single shared `Jinja2Templates` instance pointed at `templates/`.

**Error handling**: `routers/errors.py:http_exception_handler` is registered for 404s in `main.py` and renders `templates/404.html`; other HTTP exceptions fall back to a plain text response.

**Request logging**: `middlewares/request_logging.py` is attached as global HTTP middleware in `main.py`. It logs method, path, client IP, status, and duration for every request (logger name `infosys.request`); exceptions are logged then re-raised. Route-specific loggers (e.g. `infosys.api.plus`) also log at the handler level.

**No-cache for authenticated paths**: `middlewares/no_cache.py` is also attached as global HTTP middleware; it stamps `Cache-Control: no-store, no-cache, must-revalidate` + `Pragma: no-cache` on any response whose path starts with one of `NO_CACHE_PATH_PREFIXES` — currently `/admin`, `/crm`, `/api/admin`, `/api/task`. Without this, a browser can serve a previously-rendered authenticated page (or a JSON response from an admin-gated API) from its own cache (e.g. via back/forward navigation) without ever hitting the server — which looks exactly like "wasn't asked to log in" even though the session/role check never ran. Any new authenticated path (page or API) needs its prefix added here.

**Static assets**: `CSS/` and `js/` are mounted directly as `StaticFiles` at `/CSS` and `/js` (not under a combined `/static` prefix). `templates/base.html` and `templates/base1.html` (see "Two templates for the top-level shell" above) both load Bootstrap 5 and Bootstrap Icons from jsdelivr with real (curl+`openssl dgst -sha384`-computed, not fabricated) SRI `integrity` hashes — regenerate the hash in both files the same way if the pinned version ever changes.

**Configuration via `.env`**: `main.py` calls `load_dotenv(Path(__file__).resolve().parent / ".env")` as the very first thing it does, before any local import — this must stay before `from core.auth import SESSION_SECRET_KEY` specifically, since that constant is read from `os.environ` at import time (`core.firm_search`'s `ANTHROPIC_API_KEY` read is call-time, inside `search_firms()`, so it doesn't have the same ordering constraint, but loading `.env` up front covers both uniformly). `.env` (real values, per-machine) is listed in `.gitignore` and must never be committed; `.env.example` (checked in) documents which keys exist with empty placeholder values — copy it to `.env` and fill in real values on a new machine. `python-dotenv` is in `requirements.txt` for this. Currently three keys: `ANTHROPIC_API_KEY` (required for `/crm/firm_finder`'s search — see "Firm finder" below), `ANTHROPIC_MODEL` (optional, defaults to `claude-sonnet-5` in `core/firm_search.py` if unset), and `SESSION_SECRET_KEY` (optional; falls back to an insecure hardcoded dev value if unset, see "Authentication" below — set it in `.env` for anything beyond local dev).

**Data layer (SQLModel + Alembic)**:
- `db/database.py` supports two databases: if `DATABASE_URL` is set in `.env` (e.g. a Postgres/Neon connection string), that's used as `DB_URL` via a plain `create_engine(DB_URL)`; if unset, it falls back to the local SQLite file (`data/infosys.db`, `StaticPool` + `check_same_thread=False` — needed only for the SQLite case, since it's a single file shared across the app's threads; a real server DB doesn't need or want this) — `IS_SQLITE = DB_URL.startswith("sqlite")` branches between the two engine-construction paths. Switching back to local SQLite is just removing/commenting out `DATABASE_URL` in `.env` — no code change. `get_session()` (a `Session(engine)`-yielding FastAPI-dependency generator) is unaffected either way, wired via `Depends(get_session)` into every `/admin*`/`/crm` page handler and mutating route, plus every JSON API under `api/`.
- `db/database.py` also registers a SQLAlchemy `connect` event listener that runs `PRAGMA foreign_keys=ON` on every new SQLite connection. This is required — SQLite silently ignores foreign key constraints unless this pragma is set per-connection — and it's what makes the referential-integrity rule below actually enforced rather than theoretical.
- `db/migrate.py:upgrade_to_head()` runs `alembic upgrade head` programmatically (via `alembic.config.Config` + `alembic.command.upgrade`, pointed at the repo-root `alembic.ini` through an absolute `Path(__file__)`-derived path, so it doesn't depend on the process's CWD) and is called from `main.py`'s `lifespan` before the app starts serving. Added after a cloud deploy (FastAPI Cloud) hit `sqlite3.OperationalError: no such table: user` — `data/infosys.db` is gitignored (see below) and the deployed instance's disk starts empty, so nothing had ever created the schema there; the app used to assume `data/infosys.db` already existed pre-migrated, true for local dev (a committed/hand-migrated file) but not for a fresh deploy target. Idempotent — on an already-up-to-date DB (the normal local-dev case) it's a no-op, verified by moving `data/infosys.db` aside, booting the app, confirming all tables get created from scratch, then restoring the real file.

`id` + unique-indexed `name`). `models/task.py` defines `Task` (table `task`, no override needed since the default already matches): `id`, indexed `creation_date` (default-now, mirrors `User.creation_date`), indexed `author_id`/`assignee_id` (both FK → `user.id`, both required — every task must have an assignee, added via migration `07e4e837ac49` after `assignee_id` was briefly nullable), `title`, optional `description`, indexed **required** `due_date` (made required via migration `dea309ced5a4`, same reasoning/precedent as `assignee_id`), indexed `status_id` (FK → `task_status.id`), `completed` (bool, Python default `False` **and** DB `server_default=false` so a raw INSERT omitting the column doesn't hit a NOT NULL violation — mirrors the `User.isactive` precedent), indexed optional `date_finished` (added in the same migration as the `due_date` change — the actual completion timestamp; - Naming convention: multi-word columns use snake_case with underscores (`user_id`, `author_id`, `due_date`, `creation_date`, ...) — this is also the more cross-DB-portable choice, since Postgres/MySQL fold unquoted identifiers to lowercase and treat unseparated multi-word names as fragile/non-standard. SQLite doesn't auto-index FK columns (unlike Postgres/MySQL), so FK columns and date columns likely to be filtered/sorted on should get explicit `index=True`.

- **Referential integrity rule**: a row in a parent table may be deleted ONLY if no row in a dependent (child) table references it — deletes must fail loudly, not cascade. Concretely: never add `ondelete="CASCADE"` to a `foreign_key=` field or `ON DELETE CASCADE` to a hand-written migration; leaving `ondelete` unset gives SQLite's default `NO ACTION`/restrict behavior, which is what this project wants. This only works because of the `PRAGMA foreign_keys=ON` listener above — verify new FK relationships actually reject a delete-while-referenced (e.g. via a real `INSERT`/`DELETE` through `db.database.engine`), don't just trust the schema. Application code should still pre-check and surface a friendly error (see `api/task_status.py:delete_status`, which pre-checks for referencing `Task` rows *and* catches `IntegrityError` as a TOCTOU backstop) rather than letting the raw `IntegrityError` surface as an unhandled 500.
- Gotcha: Alembic's autogenerate for SQLModel `str` columns emits `sqlmodel.sql.sqltypes.AutoString(...)` in the migration body but does not add `import sqlmodel` to the generated file — add that import by hand after every `alembic revision --autogenerate` (only needed when the migration actually references `AutoString`, e.g. not for FK-only join tables).
- Gotcha: renaming a column (e.g. `user.creationdate` → `user.creation_date`) must NOT be done by accepting autogenerate's default drop-column/add-column diff — that silently drops existing data and violates NOT NULL for existing rows. Hand-write it with SQLite batch mode instead: `with op.batch_alter_table("user") as batch_op: batch_op.alter_column("creationdate", new_column_name="creation_date", ...)`. Adding an index in the same batch block as the rename that produces the renamed column hits an Alembic batch-mode bug (`KeyError` in `_gather_indexes_from_both_tables`) — split the rename and the `create_index` into two separate `batch_alter_table` blocks.

**Authentication (`/admin`)**: `get_session` has its first real consumer here. `core/auth.py` holds `hash_password`/`verify_password` (bcrypt, one-way — never store or log a raw password), `get_current_user(request, session)` (reads `request.session["user_id"]`, set by Starlette's `SessionMiddleware`, added in `main.py` with `secret_key=SESSION_SECRET_KEY` and **`max_age=None`** — Starlette's own default (`max_age=1209600`, 14 days) issues a *persistent* cookie with a `Max-Age` attribute that survives browser restarts; `max_age=None` omits `Max-Age`/`Expires` from `Set-Cookie` entirely, making it a true session-only cookie the browser discards on close, which is what this project wants (never reintroduce a numeric `max_age` here without an explicit security decision to do so). The secret key falls back to a hardcoded dev value if the `SESSION_SECRET_KEY` env var isn't set — set that env var for anything beyond local dev), `user_has_role(session, user_id, role_name)` (joins `user_role`/`role`), and `resolve_admin_access(request, session)` — the single shared state machine used by every `/admin*` page (`views/admin/admin_page.py` and `views/admin/usermgt.py` both call it rather than duplicating the branching). It returns one of four states: `"setup"` (`user` table empty → render `admin/setup.html`; password validated ≥8 chars in `views/admin/auth.py`, hashed, linked to the `admin` role via `user_role`), `"login"` (no session, or `User.isactive` is `False` — a deactivated user is treated as logged out even with a still-valid session cookie → render `admin/login.html`), `"forbidden"` (logged in, active, but lacks the `admin` role → callers `raise HTTPException(401)`), or `"ok"` (returns the `User`). Both the setup and login POST handlers, on success, just set `request.session["user_id"]` and redirect (303) back to `GET /admin`, which re-runs `resolve_admin_access` — there's no separate "authorized" code path to keep in sync. The login handler also rejects `isactive=False` accounts up front with the same generic "wrong email or password" message used for bad credentials, so disabling a user doesn't leak account status. `bcrypt` and `itsdangerous` (needed for `SessionMiddleware`) are in `requirements.txt` for this.

**Login audit log (`login_info` table, `/admin/login_info`)**: every call to `views/admin/auth.py:login()` — the single shared login endpoint for both `/admin` and `/crm` (see below) — writes exactly one `LoginInfo` row via `core.auth.record_login_attempt(session, user_id, client_ip, user_agent, status)`, whether the attempt succeeds or fails. `models/login_info.py` defines `LoginInfo` (explicit `__tablename__ = "login_info"`, same class-name-lowercasing gotcha as `TaskStatus`/`FirmType`): `id`, indexed `created` (default-now, same pattern as `creation_date` elsewhere but named `created` per how this table was specified), indexed **nullable** `user_id` (FK → `user.id` — nullable is deliberate: a login attempt against an email that doesn't match any existing user has no real user row to link to, and this table is meant to capture every attempt, including against unknown emails, not just ones against real accounts), indexed `client_ip` (`request.client.host if request.client else "unknown"` — same fallback convention as `middlewares/request_logging.py`), `user_agent` (from `request.headers.get("user-agent", "")`), `status` (free-text, internal-only reason — `"успех"`, `"пользователь не найден: <email>"`, `"пользователь отключён"`, or `"неверный пароль"`). `client_ip`/`user_agent`/`status` are all truncated to `core.auth.MAX_LOGIN_INFO_FIELD_LENGTH` (500 chars) before insert — all three originate from an unauthenticated client (headers, form fields) before any validation runs, so without a cap a client could bloat the table with arbitrarily long rows. This internal `status` detail is deliberately more specific than the single generic "Неверный email или пароль" message `login()` still shows the *user* on any failure — the merge into one generic message is an intentional anti-enumeration measure (see "Authentication" above), and logging the real reason server-side doesn't undermine that since only admins can read `/admin/login_info`. `views/admin/login_info.py:login_info_page` is a plain read-only, admin-gated (`resolve_admin_access`), paginated (`PAGE_SIZE = 30`, page-only query param, no filters — this is page 1 of the feature, add filters later if the volume actually makes that necessary) list ordered newest-first, left-joined to `User` for the email (a plain `join` would hide rows with `user_id IS NULL`). No mutations exist on this table (no delete/edit) — it's a pure audit trail.

**Authentication for any-logged-in-user pages (`/crm`)**: `core/auth.py:resolve_authenticated_access(request, session)` is the lighter-weight sibling of `resolve_admin_access` — same "login" (`("login", None)`) vs. "ok" (`("ok", user)`) states, but **no role check and no "setup"/"forbidden" states**: any active authenticated user passes, regardless of role. `views/crm/crm_page.py` calls it and, on `"login"`, renders the *same* `admin/login.html` template/`/admin/login` endpoint used by `/admin` — this project has exactly one login mechanism, shared across all authenticated pages, not a `/crm`-specific one (the template/route names still say "admin" for historical reasons; that's a known naming wart, not a bug). To make "log in, then land back on the page you actually wanted" work, the login form carries a hidden `next` field (defaults to `/admin`); `views/admin/auth.py:login()` validates it with `_SAFE_NEXT_RE = re.compile(r"^/(?!/|\\)")` before redirecting — a plain `next.startswith("/") and not next.startswith("//")` check is **not enough**, since browsers normalize a leading `/\` into a protocol-relative `//` (open-redirect bypass); the regex additionally rejects a backslash right after the leading slash. Any future authenticated-only page should reuse `resolve_authenticated_access` + the same login-with-`next` pattern rather than inventing a new one.

**User management (`/admin/usermgt`)**: single-page list of all users (`views/admin/usermgt.py:usermgt_page`), admin-gated via `resolve_admin_access` like `/admin` itself. The table itself is deliberately minimal — **only** email (clickable), full name, and an active/inactive toggle switch — with everything else (profile editing, role assignment, password change) moved into a per-user modal card, opened by clicking the email. This was a deliberate redesign (the table used to show every field and every role-management form inline, making it wide and cluttered) and is also the point where this page first got the ability to edit a user's email/fullname/name or change their password at all — neither existed before.

The card's content isn't fetched via AJAX — `usermgt_page` still renders one `<template id="user-card-{{u.id}}">` per user (containing the edit form, role badges/assign/create forms, and a password-change form that starts hidden behind a "Сменить пароль" toggle button), and `js/usermgt.js` just clones the matching `<template>`'s content into a single shared Bootstrap modal (`#userCardModal`) on email click — `template.content.cloneNode(true)` + `appendChild`, never `innerHTML`, since the content was already Jinja-escaped server-side (same DOM-API convention as `taskstatus.js`/`city.js`). This keeps the page's existing form-POST-and-303-redirect mutation style (per "Two mutation styles coexist on purpose" above) rather than introducing a JSON API for what's still a low-traffic admin page.

After any mutation (edit, role assign/remove/create, password change), the handler redirects to `/admin/usermgt?open_user_id={id}` (and `&user_error=...` on a validation failure) instead of a bare `/admin/usermgt` — `usermgt_page` reads those query params and passes them to the template as `window.OPEN_USER_ID`/`window.OPEN_USER_ERROR`, and `js/usermgt.js` reopens that user's card on load (stripping the params from the URL via `history.replaceState` afterward) — the same "reopen where you left off" idea as `open_firm_id` for `/crm/firms`, just passed through server-rendered globals rather than client-side `URLSearchParams` reading, since there's no nested return-to URL to preserve here. `toggle_active` deliberately keeps redirecting to a bare `/admin/usermgt` — the toggle switch lives in the table, not the modal, so there's no card to reopen. On an `edit_user` validation failure (empty field, duplicate email), the redirect also carries the admin's *submitted* (rejected) values (`edit_email`/`edit_fullname`/`edit_name` query params) — without this, the reopened card would silently show whatever's still in the DB instead of what was actually typed, forcing the admin to retype it; the template only substitutes these in place of the real `u.email`/`u.name`/`u.fullname` when `open_user_id` matches that specific user **and** an edit error is present (`open_user_email is not none`), so a role-management or password error elsewhere doesn't accidentally blank these fields.

`edit_user` (email/fullname/name) and `change_password` (new+confirm, reuses `MIN_PASSWORD_LENGTH` from `views/admin/auth.py`) are both new mutating routes — email uniqueness is checked the same pre-check-plus-`IntegrityError`-backstop way as `create_user`/`task_status`'s rename endpoint. Both are also the first forms in this project protected by a CSRF token: `_get_or_create_csrf_token()` lazily stores a random token in `request.session` (the same session dict `core.auth` already uses for `user_id`) and `usermgt.html` renders it into a hidden field on both forms; `_verify_csrf()` checks it via `hmac.compare_digest` before either handler does anything, 403-ing otherwise. This is deliberately scoped to just these two new routes, not a project-wide CSRF framework — `change_password` in particular is the first action in this app capable of a silent full account takeover (an admin's session performing an unwanted password change on any account), which is a materially bigger blast radius than the older, un-CSRF-protected role-assignment/toggle-active forms; revisit if those need the same treatment later, but this task didn't expand scope to cover them.

A "+ Добавить пользователя" button links to `/admin/usermgt/new` (GET shows the form, POST creates — same page/handler split as `/admin` setup vs login), which validates the password length (reuses `MIN_PASSWORD_LENGTH`) and rejects a duplicate email before creating the row; the new user starts with `isactive=True` and no roles, assigned afterward from the list. All mutating actions are POST routes under `routers/admin_usermgt.py`.

**Task statuses (`/admin/taskstatus`), cities (`/admin/city`), firm types (`/admin/firmtype`), units of measurement (`/admin/unit`) — the AJAX reference pages**: unlike `usermgt` above, these pages' mutations are **not** form-POST + redirect. Each `views/admin/*.py` page handler (`taskstatus_page`/`city_page`/`firm_type_page`/`unit_page`, all admin-gated via `resolve_admin_access`, registered as normal `PageRoute`s) does the initial server-rendered Jinja list only; every create/rename/delete action is a `fetch()` call from the matching `js/*.js` file to the matching JSON API in `api/*.py` (`POST/PATCH/DELETE /api/admin/<resource>...`), and the JS updates the DOM directly (append/replace/remove a `<tr>`) instead of the browser doing a full page reload. `task_status` is the original; `city`/`firm_type`/`unit` are faithful copies of it (same structure, different Cyrillic labels; originally no in-use delete-guard since nothing FKed to them, but `firm_type` gained one once `PartnerApplication.claimed_type_id` became the first FK pointing at it — see "Partner application questionnaire" below — the other two still have none as of this writing). This is the pattern to copy for any future "list with lots of small per-row actions" admin page — see the "Two mutation styles coexist on purpose" note above for when to pick this over form-POST. At n=4 near-identical implementations, this is still deliberately *not* consolidated into a generic/parameterized CRUD helper — explicitly reconsidered when `unit` (the 4th) was added, and the decision was to keep copying rather than refactor the three already-working pages; revisit again only if a 5th or 6th such resource shows up and the duplication starts to actually hurt. Three things worth preserving if you touch this code:
- `js/taskstatus.js`/`js/city.js`/`js/firm_type.js`/`js/unit.js` all build new rows via `document.createElement`/`textContent`/`setAttribute`, never `innerHTML` + template-literal interpolation of a name — the latter is a live XSS vector (an admin-entered name containing markup would execute) and was deliberately fixed during development on `taskstatus.js`, then carried over correctly to the others. Keep new dynamic-content insertion in these files (and any future AJAX-driven page) DOM-API-based, not string-built HTML.
- Every handler in `api/task_status.py`/`api/city.py`/`api/firm_type.py`/`api/unit.py` re-checks `resolve_admin_access` itself (`_require_admin` helper, same shape as `views/admin/usermgt.py`'s) — there is no shared middleware doing this for `/api/*`, so a new JSON endpoint under `api/` for admin-only data must gate itself explicitly, the same as these do.
- Uniqueness races: `create_*`/`rename_*` in all four `api/*.py` files pre-check for a name collision *and* wrap the follow-up `session.commit()` in `try/except IntegrityError` (rollback + friendly 400) — the pre-check alone isn't enough under concurrent requests, and letting `IntegrityError` propagate unhandled produces an ugly unhandled 500 instead of the intended error message.

**Channel types (`/admin/channeltype`)**: reuses the same AJAX-inline-edit convention as the four pages above (`views/admin/channel_type.py:channel_type_page` does the initial SSR list only; `api/channel_type.py` under `/api/admin/channeltype` re-checks admin access itself via the same `_require_admin` shape; `js/channel_type.js` builds rows via `createElement`, never `innerHTML` + interpolation; create/rename pre-check a name collision *and* wrap `session.commit()` in `try/except IntegrityError`; no in-use delete-guard yet since nothing FKs to `channel_type` — same reasoning as `city`/`firm_type` at their inception) but is **not counted as a "5th" instance of that exact pattern** — it has real per-row shape differences (`is_active`/`is_input`/`is_output` bool checkboxes plus an `icon_url` text field alongside `name`, not just a bare name), so it's its own implementation rather than a literal copy, and doesn't reopen the "should this be a generic CRUD helper" question noted above. `models/channel_type.py` defines `ChannelType` (explicit `__tablename__ = "channel_type"`, same class-name-lowercasing gotcha as `TaskStatus`/`FirmType`): `id`, unique-indexed `name`, `is_active`/`is_input`/`is_output` (all `bool`, Python default `True` **and** migration `server_default=sa.true()` — same split as `Bug.isopen`/`Notification.viewed`, using SQLAlchemy's dialect-agnostic `sa.true()`/`sa.false()` helpers rather than a raw `sa.text('true')` string, which is Postgres-only syntax and would break `CREATE TABLE` on the SQLite fallback), `icon_url` (required plain string — a path like `/pic/whatsapp.svg`, no upload mechanism anywhere in this project, the admin just types/pastes a path to an existing static file). The admin table shows an `<img>` icon preview per row (updated live from the API response after a successful save, not just on page load) and 3 checkbox columns alongside the usual name/icon-path text inputs.

**`/pic` static assets**: a new top-level static mount, `app.mount("/pic", StaticFiles(directory="pic"), name="pic")` in `main.py`, added specifically for `ChannelType.icon_url` — same pattern as the pre-existing `/CSS`/`/js` mounts, registered in the same place (well before the catch-all MCP `Mount("/", ...)` at the very end of `main.py`, per the ordering rule described below). Currently holds 7 hand-drawn SVG icons (`person.svg`, `email.svg`, `viber.svg`, `whatsapp.svg`, `telegram.svg`, `instagram.svg`, `tel.svg`) — deliberately generic flat pictograms in each brand's associated color, not reproductions of the official trademarked logos (this project redistributes these as static assets, so avoiding actual brand-logo artwork sidesteps that question entirely). **Constants (`/admin/constants`)**: reuses the AJAX conventions above (admin-gated `views/admin/constants.py:constants_page` does the initial server-rendered list only; `api/constants.py` under `/api/admin/constants` re-checks `resolve_admin_access` itself via the same `_require_admin` shape; `js/constants.js` builds rows via `createElement`/`textContent` only; create/rename both pre-check a name collision *and* wrap `session.commit()` in `try/except IntegrityError`) but is **deliberately not a fifth copy of the `task_status` pattern** — two concrete differences, both explicit product decisions, not oversights:
- **No delete endpoint** — `api/constants.py` only exposes `POST ""` (create) and `PATCH /{id}` (edit name+value together); there is no `DELETE /{id}` route and no delete button in `templates/admin/constants.html`/`js/constants.js`. Once a constant exists it can be renamed or have its value changed, but not removed through this UI.
- **`updated` is server-set, never client-supplied**: both `create_constant` and `update_constant` in `api/constants.py` call `datetime.utcnow()` themselves when building/mutating the `Constant` row — `ConstantIn` (the request body for both routes) only carries `name`/`value`, no `updated` field at all, so there's no way for a client to spoof it. The admin page renders it as a plain read-only `<td>` (`.strftime("%Y-%m-%d %H:%M")` on first load, `formatUpdated()` in JS after an AJAX save), never an editable input.

**Bug reports & notifications (bug icon in the topbar → `/admin/bugs`, `/admin/notifications`)**: clicking the topbar bug icon opens a Bootstrap modal (`#bugReportModal` in `base1.html`, wired by `js/bugreport.js`) where any authenticated user (not admin-gated — `resolve_authenticated_access`) types a description and submits it to `api/bug.py:report_bug` (`POST /api/bug`). That handler creates one `Bug` row (`reporter_id` = the submitter) and fans out one `Notification` row **to every user holding the `admin` role, with no self-exclusion** — an admin who reports their own bug still gets notified about it. (An earlier version deliberately skipped notifying the reporter if they were also an admin; that was removed after it silently produced zero notifications in the — very common — single-admin case, which directly contradicted the "always notify the admin(s)" requirement. Don't reintroduce self-exclusion without re-checking this failure mode.) The whole operation is one transaction: `session.flush()` (not `commit()`) gets `bug.id` for the notification message text, and a single `session.commit()` at the end persists the `Bug` and all `Notification` rows together — don't split this back into two commits, or a failure between them leaves an orphaned, never-notified `Bug` row. `BugReportIn.title` is capped at `max_length=2000` and stripped/non-empty-validated via a Pydantic `field_validator` (not a manual post-hoc `if not title` check) so both an empty string and a whitespace-only string fail the same way, as a normal 422 validation error. `api/admin_bug.py` (`/api/admin/bug`) and `api/admin_notification.py` (`/api/admin/notification`) are the admin-gated management APIs behind `/admin/bugs` and `/admin/notifications` (`views/admin/bugs.py`/`views/admin/notifications.py`, joined to `User` for the reporter/creator/receiver email — `notifications_page` needs `sqlalchemy.orm.aliased(User)` twice since `creator_id`/`receiver_id` both point at the same `user` table). These follow the AJAX pattern above but are a *toggle+delete-only* variant with no "create" action (`PATCH .../toggle-open`, `PATCH .../toggle-viewed`, `DELETE`) — bugs/notifications are only ever created by the app logic above, never manually from the admin UI, which is a deliberate difference from `task_status`/`city`/`firm_type`, not an oversight. Neither `bug` nor `notification` currently has anything pointing at it via FK, so their `DELETE` handlers have no in-use pre-check (same reasoning as `city`/`firm_type`). The notifications bell in the topbar is still a static `0` placeholder — it isn't wired to `notification.viewed` counts yet.

**Tasks (`/crm/tasks`)**: any authenticated user (`resolve_authenticated_access`, not admin-gated) sees two Bootstrap tabs — "Выданные мной" (`views/crm/tasks.py:tasks_page` queries `Task.author_id == current_user.id`, joined to `TaskStatus` and to the assignee `User` via `sqlalchemy.orm.aliased`) and "Выданные мне" (mirror query on `Task.assignee_id`). Ownership, not role, decides what a user may do to any given `Task`, enforced entirely in `api/task.py`:
- **Author-only** (`_get_owned_task_or_404(session, task_id, current_user.id, "author_id")`): `PATCH /{id}` (full edit: title/description/due_date/assignee — `TaskEditIn`, deliberately excludes `status_id`), `PATCH /{id}/complete` (toggles `completed` and sets/clears `date_finished` via `datetime.utcnow()`), `DELETE /{id}`.
- **Assignee-only** (`_get_owned_task_or_404(..., "assignee_id")`): `PATCH /{id}/status` (`TaskStatusChangeIn`, the *only* way `status_id` changes) — the author cannot call this, the assignee cannot call any of the author-only routes above.
- `_get_owned_task_or_404` returns **404, not 403**, whether the task doesn't exist or just isn't owned by the caller — deliberately not distinguishing the two, to avoid leaking task-ID existence to users who have no relationship to that task.
- `TaskIn` (create, `POST ""`) requires a `status_id` and validates `due_date` isn't in the past (`field_validator`, compared against `datetime.utcnow().date()` — **not** `date.today()`, to stay consistent with this project's naive-UTC-everywhere convention rather than the server host's local timezone). `TaskEditIn` (edit) has **no blanket past-date rejection** — instead `edit_task` only rejects when `payload.due_date != task.due_date` **and** the new value is in the past, so an already-overdue task can still be edited (e.g. just fixing a typo) without being forced to also push its deadline forward, while actively moving a due date backward (from either past or future) is still blocked. Don't collapse this back into a single reused `TaskIn`-style field validator — it needs the existing DB row to know whether the value actually changed.
- `TaskOut` (the shared response shape for all five mutating routes, built once by `_to_task_out()`) exposes `author_fullname`/`assignee_fullname`, not email — the UI intentionally shows people's names, not their email addresses, everywhere on this page (table columns, the assignee `<select>` in the create/edit modal, and the read-only "Автор" field in the view modal below). `views/crm/tasks.py`'s user-list query for that `<select>` is likewise ordered by `User.fullname`, filtered to `User.isactive.is_(True)`.

**CRM dashboard charts (`/crm`)**: the CRM landing page shows four charts in two rows, all built by-hand in plain HTML/CSS/SVG (no charting library), following this project's data-viz methodology (the bundled `dataviz` skill).

Row 1 — two horizontal bar charts: task counts by status, one for tasks the current user authored, one for tasks assigned to them (`views/crm/crm_page.py:_status_breakdown()`, called once per chart with the shared, single pre-fetched `list[TaskStatus]` and either `Task.author_id`/`Task.assignee_id` as the ownership column — fetch `TaskStatus` once per request and pass it in, don't let each chart's helper re-query the same lookup table). A single categorical hue for every bar (each chart is genuinely one series — magnitude by status category — so no legend box is needed, the card title already says what's plotted), every status rendered even at zero count (so the full workflow is always visible, not just statuses with data), value directly labeled at the tip of each bar.

Row 2 — two donut/ring charts: firm counts by city and by firm type, **global across all users** (`views/crm/crm_page.py:_firm_city_breakdown()`/`_firm_type_breakdown()`) — unlike the task charts above, these deliberately do *not* scope to the current user, since the `firm` table is shared/unfiltered everywhere else in the app (search results, `/crm/firms`); scoping just these two charts to "my firms" would have been the one inconsistent read path on `firm` in the whole project. Unlike the task charts, **zero-count categories are omitted** here (an explicit, opposite design choice from the task charts' "show every status" rule — requested directly, not a bug if you're comparing the two). Rendered as SVG rings (`_donut_breakdown()`: multiple `<circle>` elements per chart, each stroke-dasharray'd to its slice's arc length and `rotate()`-positioned to its cumulative offset — the classic SVG-ring technique, computed server-side in Python, not in Jinja) plus an HTML legend (color swatch + label + count + percentage — text stays in text-ink colors, never the slice color, per the skill's "text never wears the data color" rule). Colors come from the skill's 8-slot categorical palette (`CATEGORICAL_PALETTE` in `crm_page.py`, validated via `dataviz`'s `scripts/validate_palette.js` for both light and dark — light mode carries a contrast WARN on 3 of the 8 slots, mitigated by the mandatory legend values + table view, per the skill's "relief rule"), assigned via `_assign_slots()` to the **full, stable list of cities/firm types ordered by id** — not just the ones currently showing — so a city's color never shifts as other cities gain or lose firms (the "recolor-on-filter" anti-pattern the skill calls out); anything past the 8th slot folds into one combined `_build_rows()`-merged "Другое" row (summed count, `OTHER_COLOR` gray) rather than staying as separate same-colored rows — the latter was a real bug caught in review: `_assign_slots()` only maps entities into the *first 8* palette slots (not a per-entity fallback to `OTHER_COLOR`), specifically so `_build_rows()`'s `entity_id in colors` check can tell "has its own slot" apart from "needs folding into Other"; without that, two different 9th/10th-category entities would render as two visually-identical, often-adjacent gray arcs with no way to tell them apart on the ring itself. Gotcha: `DONUT_RADIUS`/`DONUT_STROKE_WIDTH` (both in `crm_page.py`, passed into the template) must satisfy `radius + stroke_width/2 < 70` (the SVG `viewBox="0 0 140 140"` half-dimension) or the ring's outer edge gets clipped by the SVG's default `overflow:hidden` at the top/bottom/left/right — caught in review after the first pass used `r=60, stroke-width=28` (outer edge 74 > 70); current values (`r=50, stroke-width=24`, outer edge 62) leave an 8-unit margin. **No dark-mode variant is implemented for either row of charts** — a deliberate deviation from the skill's own "dark mode is selected, not automatic" rule: this whole application has no dark-mode support anywhere else (no `data-theme`, no `prefers-color-scheme` handling in any other template), so shipping dark colors for two isolated chart cards would look broken against an otherwise all-light Bootstrap page rather than better; revisit if the app ever adopts a real theme toggle.

Both ring segments and their matching legend rows are **clickable**, linking to `/crm/firms?city_id=<id>` / `?type_id=<id>` (the "Другое" overflow row, `id=None`, links nowhere — there's no single filter value that represents it) — clicking a slice jumps straight to the already-filtered firm list. Each slice's visible arc is deliberately paired with a second, invisible, much-fatter arc (`DONUT_HIT_RADIUS`/`DONUT_HIT_STROKE_WIDTH` in `crm_page.py`, `opacity="0"`) sharing the exact same `rotate()`/percentage-derived angular span, widening the real click target from the thin painted ring out to a near-full pie-wedge (radius 0 to 68, i.e. almost the full 70-unit viewBox half-dimension) — the visible ring alone is a "pinpoint hit target" (the anti-pattern the skill's `interaction.md` calls out), too thin and precise to click reliably, especially since the donut's hollow center is dead space with nothing under the pointer. Gotcha found while verifying this in a real browser: **don't assume the ring's largest slice starts exactly at 12 o'clock in screen space** — the `rotate(rotate_deg - 90 ...)` transform's start point is correct by construction (verified via `elementFromPoint` sweeps at 10° increments all the way around), but the browser's own default start-point/sweep-direction for a plain `<circle>`'s implicit stroke path is an implementation detail this codebase doesn't control, so the *visual* seam between the last and first slice lands a bit clockwise of true 12 o'clock rather than exactly on it — cosmetic only (every slice still reliably links to its own city/type with no cross-wiring; verified empirically, not just asserted), not worth chasing further unless it becomes visually objectionable.

Every chart card has a "Таблица" toggle (the accessibility table-view twin) that **only renders when that chart actually has data** — don't bring back an unconditional toggle button, it was a dead control with nothing to toggle when a chart is empty (see the empty-state guards in `templates/crm/crm.html`, which suppress both the toggle button and the chart/table pair together; for the donut charts this is simply `{% if firm_city_chart %}`/`{% if firm_type_chart %}` since those lists are already pre-filtered to non-zero categories). `js/crm_charts.js`'s `wireTableToggles()` is fully generic on `data-chart`/`${key}-chart-view`/`${key}-chart-table` — the two new donut charts needed zero JS changes, they just plugged into the existing toggle wiring by using the same id/data-attribute convention. Visual QA for changes here should include an actual rendered screenshot (a headless-Chromium Playwright script driving the real dev server is the established way to do this in this environment, not just an HTTP-level assertion), not just a data-correctness check via `TestClient`.

**Search sources for partner lead-gen (`models/search_*.py`)**: a small, deliberately-scoped reference dataset — not (yet) exposed through any page or API — describing *where to look* when manually or semi-automatically researching potential B2B partner companies by city (door stores, interior-design studios, developers, repair contractors), each keyed by a stable `SearchCategory.key` slug (e.g. `"door_stores"`) rather than the Russian display label. Seeded once from an external `search_sources.json` (not part of this repo) via a one-off script run manually with the project venv — **no admin UI exists for this data yet** (that was an explicit scope decision, not an oversight); if one is added later, follow the `task_status`/`city`/`firm_type` AJAX pattern above rather than form-POST, and add an in-use delete-guard the same way once anything depends on it.

**Firm finder (`/crm/firm_finder`)**: any-authenticated-user page (`views/crm/firm_finder.py:firm_finder_page`, `resolve_authenticated_access` like `/crm/tasks`), linked from the `/crm` landing page next to "Мои задачи". Shows two `<select>` dropdowns — cities from `City`, firm types from `FirmType` (both ordered by `.name`) — and a "ПОИСК" button (`js/firmfinder.js`) that `fetch()`s `POST /api/firm/search` with the chosen `city_id`/`type_id` and renders the returned firms into a results table (built via `document.createElement`/`textContent`, never `innerHTML` + interpolation, same XSS-avoidance convention as `taskstatus.js`/`city.js`). **Deliberately not linked to the `search_*` reference tables** (`SearchCategory`/`SearchQueryTemplate`/`SearchDirectory`) — that was an explicit scope decision, since `FirmType`'s categories (own free-form classification: фабрика дверей, магазин дверей, дизайн студия, конкурент, партнер, конечный потребитель, неизвестно, ...) don't correspond 1:1 with `SearchCategory`'s four lead-gen categories (door_stores/design_studios/developers/contractors), and no mapping between the two exists yet; revisit only if that mapping gets designed later.

`api/firm.py:search()` (`POST /api/firm/search`, any authenticated user) validates `city_id`/`type_id` exist, calls `core/firm_search.py:search_firms(city_name, firm_type_name)`, then inserts one `Firm` row per result with `user_id` = the calling user — **not admin-gated, not ownership-gated on read**: any authenticated user can search and any authenticated user's search results land in the same shared `firm` table (there's no per-user filtering of past results anywhere yet). Application-level dedup only (no DB unique constraint): before inserting, it pre-loads existing `Firm.name` values for that `(city_id, type_id)` pair (case/whitespace-insensitive) and skips any result that already matches, both against the DB and within the same batch — this is intentionally soft (a DB-level unique constraint was not added, since two genuinely different companies could legitimately share a name across different searches, and this is lead-gen data meant to be reviewed by a human, not treated as authoritative).

`core/firm_search.py:search_firms()` is **the actual search implementation — and it does not call any web-scraping code or any of this project's own HTTP stack**. It calls the real Anthropic Messages API (the `anthropic` Python SDK, now in `requirements.txt`) from the backend process itself, with the server-side `web_search` tool enabled (`{"type": "web_search_20260318", "name": "web_search", "max_uses": 5}`) — this runs entirely server-side on Anthropic's infrastructure; **it does not require Claude Desktop or Claude Code running anywhere**, client or server, it's a plain synchronous API call like any other outbound HTTP request this app makes. A system prompt instructs the model to search the web for real companies of the given type in the given city and answer with *only* a JSON array (no markdown fencing, no prose) matching a fixed shape (`name` required, `phone`/`website`/`address`/`source`/`notes` nullable); `_parse_results()` delegates the "JSON-only, but maybe still fenced/prefaced" parsing to the shared `core/ai_json.py:parse_json_array()` (strips an accidental code fence, then scans for the first *balanced* `[...]`, tracking string/escape state so a bracket inside a quoted value, or in trailing wrap-up prose the model adds despite being told not to, doesn't fool a naive first-`[`/last-`]` match — this replaced an earlier, buggier version duplicated inline in this file, and the identical logic is now shared with `core/firm_price_download.py` rather than re-duplicated a second time), then silently drops any entry missing a non-empty `name`, capped at `MAX_RESULTS = 10`. Requires `ANTHROPIC_API_KEY` to be set in `.env` (see "Configuration via `.env`" above; read via `os.environ.get`, same pattern as `SESSION_SECRET_KEY` in `core/auth.py`, but **no insecure hardcoded fallback here** — a missing key raises `FirmSearchError` immediately, which `api/firm.py` turns into a `502` with a Russian error message). Network/API failures (`anthropic.APIError`) and unparseable responses both raise `FirmSearchError` the same way, so the frontend always gets a plain-text `detail` to show in `#firmFinderError`, never a raw traceback. Because a real web-search-backed model call with several sequential tool round-trips (`max_uses=5`) can legitimately take a few minutes, `js/firmfinder.js` disables the button and swaps in a spinner for the duration — there is no background job/task queue in this project, this is a plain synchronous request held open for the duration of the call. The `anthropic.Anthropic` client is constructed with an explicit `timeout=240.0, max_retries=0` (rather than the SDK's own defaults) — bounded so a degraded Anthropic API can't tie up one of this app's shared threadpool workers indefinitely, but generous enough for a real multi-search-round-trip response (an earlier `timeout=90.0, max_retries=1` was too aggressive in practice: a slow-but-legitimate search hit the 90s cap, the SDK retried once by default on the timeout, and the request failed at ~180s even though it likely would have succeeded given more time — `max_retries=0` now avoids that silent doubling). `MODEL` is read from `ANTHROPIC_MODEL` (falls back to `"claude-sonnet-5"`) rather than hardcoded, so the model can be swapped per-environment via `.env` without a code change.

**Firm list (`/crm/firms`)**: any-authenticated-user page (`views/crm/firms.py:firms_page`, `resolve_authenticated_access`), linked from `/crm` next to "Мои задачи". Each row still needs to resubmit its (unchanged) `channel_id` on every `PATCH` since `FirmChannelIn.channel_id` is required by the API — the template stamps it as `data-channel-type-id` on the `<tr>` (`js/firm_channels.js`'s `buildRow()` mirrors this via `row.dataset.channelTypeId`), and `readPayloadFromRow()` reads it from there rather than from a form control. Because the per-row type `<select>` is gone, `js/firm_channels.js` no longer needs the full `(id, name)` list of channel types client-side, so `window.ALL_CHANNEL_TYPES`/`all_channel_types_json` (previously built server-side in `views/crm/firm_channels.py` the same way `usermgt.html` builds `window.OPEN_USER_ID`) were removed along with it — only `active_channel_types` (for the "add new channel" `<select>`, `is_active=True` only) remains.

**Firm events (`/crm/firms/{firm_id}/events`)**: a fourth button in the `#firmModal` header, `#firmModalEventsLink` — same show/hide wiring and `return_to`-carrying URL construction as the three above. `models/firm_event.py` defines `FirmEvent` (explicit `__tablename__ = "firm_event"`, same class-name-lowercasing gotcha as `TaskStatus`/`FirmType`/`FirmChannel`): `id`, indexed `channel_id` (FK → **`firm_channel.id`, not `channel_type.id`** — deliberately the same field name as `FirmChannel.channel_id` but pointing at a different table; an event is a log entry against one specific channel *instance* of a firm, e.g. "called +380...", not against a channel type in the abstract), `created` (default-now, `server_default=sa.text('(CURRENT_TIMESTAMP)')` — same cross-dialect pattern as `FirmChannel.date_added`, and likewise **not indexed**, per how this table was specified), indexed **required** `user_id` (FK → `user.id` — the event's original author; unlike `Task.status_id`-vs-`completed` there's no separate "editor" field, so this stays the creator even after a later correction, see below), `description` (required text). Unlike `firm_channel` (owner/admin-only CRUD) but like `firm_comment` (any authenticated user), viewing/adding/editing is open to **any authenticated user**, gated only by `_require_authenticated` — an explicit product decision for this table specifically, not a copy-paste of one existing pattern over the other. Unlike `firm_comment` (append-only, no edit), **editing is allowed** (`PATCH`) but **deleting is not** — also explicit: "что написано пером — не вырубишь топором" (what's written stays written, but can be corrected). `edit_firm_event` never reassigns `user_id` to the editor — the original author is preserved across corrections, the same way `Task.author_id` never changes.

`views/crm/firm_events.py:firm_events_page` is the **first firm sub-page with real server-side pagination** (`PAGE_SIZE = 10`, `?page=` query param, page-clamping — structurally copied from `views/admin/login_info.py`'s simpler prev/current/next style rather than `firms_page`'s windowed-page-number style, since there's only one filter dimension here: the firm itself). Because `FirmEvent` has no direct `firm_id` column, every query (`total` count and the page of rows) joins through `FirmChannel` (`FirmEvent.channel_id == FirmChannel.id`) and filters `FirmChannel.firm_id == firm_id`, then further joins `ChannelType` (for display) and `User` (for `author_fullname`); ordered newest-first (`FirmEvent.created.desc(), FirmEvent.id.desc()`). The page also queries the firm's own `FirmChannel` list (joined to `ChannelType` for a human-readable `"{type}: {address}"` label) to populate the channel `<select>` in both the add-form and each row's inline edit — if the firm has zero channels yet, the add-form is replaced with a message linking to "Каналы связи" to add one first, since an event can't exist without a channel to attach to.

`api/firm.py` adds `_get_firm_event_or_404` (mirrors `_get_firm_channel_or_404`'s shape but one level deeper: loads the `FirmEvent`, then loads its `FirmChannel` and checks `channel.firm_id == firm_id`, so one firm's events can't be read/edited through another firm's URL — the same IDOR guard pattern used throughout `api/firm.py`) plus `add_firm_event`/`edit_firm_event` (`POST/PATCH /api/firm/{firm_id}/events[/{event_id}]`). Both validate the submitted `channel_id` via the existing `_get_firm_channel_or_404` (so a `channel_id` belonging to a *different* firm is rejected the same way editing a channel through the wrong firm's URL is), which doubles as the check that the value in `FirmEventIn.channel_id` actually is a `firm_channel.id` and not, say, a stray `channel_type.id`. `created` is never client-settable (server-set via `default_factory=datetime.utcnow` at insert time only, absent from `FirmEventIn` entirely).

The page (`templates/crm/firm_events.html`, `js/firm_events.js`) mixes both existing AJAX conventions rather than picking one: rows are edited **in place** the `firm_channel`/`channel_type` inline-edit-in-table way (a `<select>` + text input per row, "Сохранить" button, `PATCH` via `fetch`, `row.replaceWith(buildRow(...))` on success — no delete button, since none exists) — but **adding** a new event does a plain `window.location.reload()` on success, the `firm_comments`/"Скачать прайс" way, rather than appending a DOM row — because a new event is always the newest by `created` and could belong on a different page than whatever page the user is currently viewing (page 2, 3, ...); reloading re-runs the same paginated query server-side rather than duplicating that sort/page logic in JS. `window.FIRM_CHANNELS` (a plain `id`/`label` list, same "server-built plain dicts, since Jinja `|tojson` can't serialize SQLModel ORM objects" technique as `window.ALL_CHANNEL_TYPES` on the channels page) is embedded so `buildRow()` can populate a freshly-`PATCH`ed row's `<select>` without a round-trip.

Adding `FirmEvent.channel_id` as the **first FK ever pointing at `firm_channel.id`** exposed a real pre-existing gap, caught in code review: `api/firm.py:delete_firm_channel` used to unconditionally `session.delete(channel); session.commit()` with no in-use guard (previously safe, since nothing referenced `firm_channel` at all) — deleting a channel that still had `FirmEvent` rows pointing at it now raised an unhandled `IntegrityError` (a raw 500, no rollback) under the project's referential-integrity rule (no `ondelete=CASCADE` anywhere, deletes must fail loudly). Fixed the same way `task_status.py:delete_status` handles this: `delete_firm_channel` now pre-checks for a referencing `FirmEvent` and returns a friendly `400` if found, plus wraps the delete/commit in `try/except IntegrityError` as a TOCTOU backstop.

**Global events page (`/crm/events`)**: a "События" button on the `/crm` dashboard (`templates/crm/crm.html`, alongside the existing "Мои задачи"/"Фирмы" buttons) links to `views/crm/events.py:events_page` — the same `FirmEvent` data as the per-firm page above, but **listing events across every firm in the system**, not scoped to one firm (an explicit product decision, same "global, not per-user" shape as the `/crm/firms` list and the `/crm` donut charts). Same `resolve_authenticated_access` gate, same `PAGE_SIZE = 10` server-side pagination style as `firm_events_page`. **Unlike most other "drill-down" firm sub-pages, this one is reached directly from the CRM dashboard, not from a firm card**, so it has no `return_to`/`close_url` machinery — it's a standalone top-level page, same as `/crm/tasks`/`/crm/firms`.

Per an explicit product decision ("чтобы менеджеру было проще"), this page has **full view/add/edit capability**, not just a read-only rollup — it deliberately reuses the exact same `api/firm.py` routes (`POST/PATCH /api/firm/{firm_id}/events[/{event_id}]`) the per-firm page uses, rather than adding new global-scoped API endpoints; the page/JS just supplies whichever `firm_id` is relevant (the row's own firm for edits, the selected firm for a new event) when building each request URL. This means every IDOR/ownership guard already enforced by those routes (`_get_firm_channel_or_404`/`_get_firm_event_or_404` checking `channel.firm_id == firm_id`) applies unchanged here too — the global page cannot weaken them, it just calls the same validated endpoints from a different UI.

Two new columns not present on the per-firm page: **Фирма** and **Город** (plain text, not editable — an event's firm is fixed at creation via which channel it's attached to, and there's no "move to a different firm" operation, consistent with `Task.author_id` and `FirmEvent.user_id` never being reassignable elsewhere in this project). `views/crm/events.py` builds `channels_by_firm` (a `dict[firm_id, list[{id, label}]]` from one bulk `FirmChannel`+`ChannelType` query) once per request and reuses it both to populate each existing row's channel `<select>` (scoped to that row's own firm only — same IDOR-safety property as the per-firm page's per-row select) and to build `firms_with_channels` (every firm + its city label + its own channel list) for the add-form's **cascading `<select>`s**: choosing a firm in `#eventNewFirm` repopulates `#eventNewChannel` from that firm's own channel list (`js/events.js`, `window.FIRMS_WITH_CHANNELS` embedded the same server-built-plain-dict way as `window.ALL_CHANNEL_TYPES`/`window.FIRM_CHANNELS` elsewhere) — a firm with zero channels shows a disabled "— у фирмы нет каналов связи —" placeholder instead of an empty/broken `<option>` list. Saving an edited row (`js/events.js:saveRow()`) reconstructs the row via the same `buildRow()`-then-`replaceWith()` pattern as `firm_events.js`, but since `FirmEventOut` carries no firm/city info (an edit never changes them), `firm_name`/`city_name` are read back from the row's own existing `<td>` text before the request fires, rather than expecting them in the API response. Adding a new event still does a plain `window.location.reload()` on success (same reasoning as the per-firm page: a brand-new event is always the newest, and may not even belong on the page/firm the user is currently viewing, so re-running the paginated query server-side is simpler and always correct).

**Downloading a firm's price list via AI ("Скачать прайс")**: `core/firm_price_download.py:download_firm_price(firm_name, website)` (now `async def`) is **not** an agentic tool-use call like `core/firm_search.py:search_firms()` — it's a self-driven pipeline: this project's own code (via `httpx.AsyncClient` + `BeautifulSoup`) fetches and parses the firm's site — `beautifulsoup4` is newly added to `requirements.txt` for this; `httpx` was already present transitively via `fastapi`/`anthropic`, but `requirements.txt` had it misdeclared as a typo'd, unrelated package literally named `httpx2` (caught in the same review pass as the bugs below and fixed to just `httpx` — harmless in practice since the real `httpx` was always installed anyway via the transitive chain, but worth declaring correctly now that this file imports it directly), and Claude is only asked to extract structured data from text this code already downloaded (`client.messages.create()`, no `tools=[...]` at all). This is a **deliberate departure** from an earlier, abandoned agentic design (`tools=[web_search, web_fetch]`, letting the model decide what to fetch and when) — see the "Why not agentic tool-use" note below for the concrete failures that motivated the rewrite. `firm_search.py` still uses the simpler agentic `web_search`-only approach unchanged, since finding a *handful of companies* from search snippets is a much smaller, well-bounded problem than crawling one specific site's catalog for exact prices. Both modules share `core/ai_json.py` (`strip_code_fence`/`extract_balanced_json_array`/`parse_json_array`/`AiJsonError`) for turning a "JSON-only" LLM response into an actual list, since a model asked for JSON-only still sometimes wraps it in a code fence or adds prose either side of it.

The pipeline, in order:
1. **Fetch the homepage** (`httpx.AsyncClient`, a real desktop-browser `User-Agent` — many small-business WordPress/OpenCart sites block requests with no/suspicious UA via basic anti-bot plugins; this isn't evasion, just a realistic default so a single, low-frequency, legitimate fetch isn't trivially blocked).
2. **Find candidate "door" pages** by scanning the homepage's own links (`_extract_candidate_links`): same-domain hrefs whose visible text or URL path matches `_DOOR_LINK_RE` (`двер|dver|door`, covers двери/дверь/дверной/dveri/door in Russian/Ukrainian/English), capped at `MAX_CANDIDATE_PAGES = 6`.
3. **Fetch the homepage + those candidate pages concurrently** (`_fetch_pages`, `asyncio.gather` bounded by an `asyncio.Semaphore(FETCH_CONCURRENCY)` — deliberately throttled, not one request per candidate fired unbounded, out of scraping etiquette toward a small firm's own server) — a failed/timed-out individual fetch is logged and skipped, never aborts the whole download.
4. Each successfully-fetched page is converted from HTML to plain text **with links preserved inline** (`_html_to_text_with_links`: `<script>`/`<style>`/etc. stripped via BeautifulSoup, then every `<a href>` is replaced with `"anchor text [absolute URL]"` before extracting `get_text()`) — this is the key trick that lets the *next* step ask Claude for a specific product's URL when its price isn't on the page it's currently reading, since a plain `get_text()` would have thrown the href away. Capped at `MAX_PAGE_CHARS` per page.
5. **First Claude extraction pass** (`_extract_items`, one plain non-tool `messages.create()` call over all fetched pages' text): for each door item, return `name`/`article`/`unit`/`price`, and — *only* when `price` couldn't be found on the page being read — a `url` copied from one of those inline `[URL]` markers, so this code knows exactly which specific product page to fetch next. Windows/balconies are excluded by the same system-prompt rule as before, including the "the whole site's theme is windows, but it may still have a separate doors section — check anyway" clarification (still needed, this code doesn't do that reasoning itself).
6. **Second round**: every returned item with `price: null` and a same-domain `url` becomes a pending fetch (capped at `MAX_PENDING_PAGES = 40`, same-domain-restricted via `_same_domain()` so a hallucinated or off-domain URL is simply ignored, not fetched) — fetched concurrently the same way, then run through **one more** `_extract_items()` call to pull the price/article/unit off each product's own page.
7. Round 1 + round 2 items are concatenated and passed through `_parse_results()` (unchanged in spirit from before: drop anything without a `name` or a `price`, cap at `MAX_RESULTS = 80`) — the final `list[dict]` shape (`name`/`article`/`unit`/`price`) is **identical** to what the old agentic version returned, so `api/firm.py`'s `_prepare_price_items()`/`download_price()` downstream logic (article splitting/slugifying/deduping, unit resolution, `FirmPrice`/`FirmGoods`/`FirmPriceBody` writes) needed **zero changes** for this rewrite — only the `await` at the call site, since `download_price()` is now `async def` too (so the multi-second-to-low-minutes pipeline doesn't tie up a FastAPI sync-route worker thread for its whole duration).

Five bugs caught in code review of this rewrite (all fixed, all in `core/firm_price_download.py`), worth knowing about if this file is touched again:
- **SSRF via redirects to private/internal addresses**: moving the actual HTTP fetch onto this app's own server (instead of Anthropic's infrastructure doing it, as the abandoned agentic design did) introduces a real SSRF surface, since `Firm.website` is settable by any authenticated user (see "Firm list" above) and a same-domain URL can still 302 to an attacker-chosen target. Fixed by turning off httpx's own `follow_redirects` and having `_fetch_page` walk redirects itself (capped at `MAX_REDIRECTS = 5`), re-validating every hop with `_is_safe_url()` — rejects any non-`http`/`https` scheme (blocks `javascript:`/`file:`/etc.) and any literal private/loopback/link-local/reserved/multicast IP (via the stdlib `ipaddress` module — blocks `127.0.0.1`, `169.254.169.254` cloud-metadata, `10.x`/`192.168.x` internal ranges, etc.). This is a deliberately proportionate mitigation for a demo/internal-tool project (no DNS-rebinding-safe resolution hook), not a hardened security boundary.
- **Relative links resolved against the pre-redirect URL**: `_fetch_page` used to discard the actual final URL reached after any redirect and hand back only the originally-requested one, so `urljoin()` on a redirected page's relative hrefs (e.g. `http://site.com` → `https://site.com/store/`) silently produced wrong absolute URLs, quietly dropping otherwise-reachable pages. Fixed as a side effect of the SSRF fix above — `_fetch_page`/`_fetch_pages` now return the actual post-redirect URL alongside the HTML, and every `urljoin()` base in `download_firm_price()` uses that.
- **Image-only anchors lost their URL entirely**: `_html_to_text_with_links` only embedded `"text [URL]"` when the anchor had visible text; a textless anchor (extremely common on real catalogs — a product card wrapped only around a thumbnail `<img>`) got replaced with an empty string, silently discarding the one thing the whole two-round design depends on. Fixed: a textless anchor now still becomes a bare `"[URL]"`.
- **A round-2 failure discarded round-1's already-good results**: if the second `_extract_items()` call (fetching the "no price shown" product pages) hit a transient Claude API error, that exception used to propagate out of the whole `download_firm_price()` call, throwing away round 1's perfectly good items too. Fixed: round 2 is now wrapped in its own `try/except FirmPriceDownloadError`, logging a warning and falling back to round-1-only results — consistent with every other failure path in this module (an individual page fetch failing was already non-fatal; a failing *second extraction pass* should be too, since it's explicitly a best-effort follow-up).
- **The `anthropic.AsyncAnthropic` client was never closed**: constructed as a bare object with no `async with`/`.close()`, unlike the `httpx.AsyncClient` right above it — could accumulate un-released connections under concurrent downloads. Fixed: `httpx.AsyncClient` and `anthropic.AsyncAnthropic` are now both entered via one combined `async with ... as http_client, ... as anthropic_client:` statement.

**Why not agentic tool-use (the abandoned earlier design)**: a single `tools=[web_search, web_fetch]` call let the model decide everything — what to search, what to fetch, when to stop — inside one opaque, unbounded turn. Live testing against real sites (`okna.zp.ua`, `dveri.zp.ua`) surfaced exactly the failure modes that kind of black-box design invites: `web_search` alone returned only short snippets (confirmed by inspecting raw tool-result blocks — the model's own `site:domain/specific-path` follow-ups came back with unrelated results, e.g. Wikipedia disambiguation pages, instead of that page's actual body), so a price sitting in a product page's body text was invisible without also enabling a `web_fetch` tool (only available in this SDK's beta namespace, `client.beta.messages.create`); even after wiring `web_fetch` in and fixing that, a single call against a larger real catalog (`dveri.zp.ua`, 52+ products in one category alone) still **timed out** at up to 900s wall-clock, with no partial results salvageable from a failed/timed-out turn and no visibility into what the model was even doing moment-to-moment; and separately, the model spontaneously invoked an always-available `code_execution` server tool to orchestrate its own `web_search`/`web_fetch` calls, adding further unpredictability neither declared nor controlled by this code. None of that is fixable by better prompting — it's a structural consequence of delegating the entire fetch strategy, page count, and pacing to the model inside one uninterruptible call. The rewrite above fixes this by keeping every fetch decision, retry, and concurrency limit in this project's own code, and reducing each individual Claude call to a small, fast, bounded, tool-free text-extraction request — the same shift in philosophy as "let the deterministic parts be deterministic," applied to network I/O instead of just JSON parsing. (One practical side-effect worth remembering if this component gets touched again: this exploration burned real Anthropic API credit over the course of finding the above — several $ worth in a single day per direct account feedback — a concrete reminder that a live-API-calling feature's *iteration* cost is not free, unlike almost everything else in this local-first demo project.)
- **`_parse_price()`'s comma-only case was ambiguous and guessed wrong on a real price**: `"8,730"` (from "від 8,730 грн") is 8730 hryvnia (comma as a thousands separator, common on Ukrainian WooCommerce sites), but the original single rule ("one comma with no decimal point nearby → treat comma as the decimal separator") parsed it as `8.73`. Fixed with a digit-count heuristic: exactly 2 digits after a lone comma → decimal separator (kopecks, e.g. `"150,50"` → `150.50`); exactly 3 digits → thousands separator, comma dropped (e.g. `"8,730"` → `8730.00`); any other digit count keeps the old decimal-separator assumption. Also added `"комплект"`/`"компл"`/`"компл."`/`"к-т"` to `_UNIT_SYNONYMS` → `"шт"` (doors are very commonly sold "as a set", per the same real product page) — previously any of these fell through to the unresolved-unit path (still safely defaulting to "шт" either way, but now via an explicit match rather than the fallback).

`api/firm.py:download_price()` (`POST /api/firm/{firm_id}/download_price`, any authenticated user — same convention as the rest of this file, not owner/admin-restricted) is the endpoint the button calls: 400 if `firm.website` is empty or doesn't start with `http(s)://`, 502 if `download_firm_price()` raises `FirmPriceDownloadError`, 422 if nothing usable came back (no `FirmPrice`/`FirmGoods`/`FirmPriceBody` rows are written in that case). `_prepare_price_items()` parses each raw item's price (`_parse_price()` — handles both comma-as-decimal and comma-as-thousands-separator ambiguity, strips currency symbols, rejects `<= 0` and unparseable values), and — only when the AI didn't already split one out — applies `_split_leading_article()` as a backend safety net (same SKU-prefix pattern as the system prompt describes; the regex requires at least one digit in the matched prefix specifically to avoid false-splitting plain material/brand abbreviations like `"МДФ"`/`"ПВХ"`, which was a real false-positive caught in review before that digit requirement was added).

Per an explicit product decision, an existing `FirmGoods` row is reused **by name**, not by article, across separate downloads (so the same physical product doesn't get re-created every time the site is re-scraped, even if the AI's article-extraction is inconsistent run-to-run) — `_dedupe_article()` only kicks in when a *new* `FirmGoods` row is actually being created, appending a `-2`/`-3`/... suffix if the article would otherwise collide with another good already on file for this firm (comparison is case-insensitive, since the same SKU can come back differently-cased across runs — also caught in review). One sharp edge this reuse-by-name policy runs into: **within a single download, the same base name can legitimately cover two different products** (e.g. two colors of "the same" door, distinguished only by their SKU prefix) — naively deduping/reusing by name alone would either silently drop the second variant or crash the whole request on the `(price_id, good_id)` uniqueness constraint (both were real bugs caught in review). The fix has two parts: `_prepare_price_items()` dedupes within a single AI response by `(name, article)` together, not name alone, so distinct articles under the same name both survive; and `download_price()` itself tracks, per name, whether more than one distinct article appeared *in this batch* — if so, every item under that name is forced to create/use its own `FirmGoods` row instead of collapsing onto whichever one happened to resolve first. Finally, the whole write (the new `FirmPrice`, any new `FirmGoods`, and every `FirmPriceBody` row) goes through one `session.flush()` (to obtain the ids `FirmPriceBody` needs) followed by one `session.commit()`, with **both** wrapped in the same `try/except IntegrityError` — an earlier version left `flush()` outside that block, so a uniqueness collision raised there (e.g. two concurrent downloads for the same firm racing on the same generated article) surfaced as an unhandled 500 with no rollback instead of the intended friendly error; this was caught in review and fixed by widening the `try` to cover both.

Since this page only exists as a drill-down from the firm card, its close control is a plain **"✕" icon** (`title="Закрыть"`), not a "back to the firm list" link. Getting this right needed more than just an `open_firm_id` query param, though — `js/firms.js`'s `openCardModal()` also captures `window.location.pathname + window.location.search` **at the moment "Прайсы" is clicked** and passes it through as a `return_to` query param on the prices-page URL (e.g. `/crm/firms/{id}/prices?return_to=%2Fcrm%2Ffirms%3Fpage%3D2` if the user had been on page 2, or with a `city_id`/`type_id`/`q` filter baked in) — an earlier version pointed the close button at a bare `/crm/firms?open_firm_id=...`, which silently landed back on page 1 with no filter, and if the firm wasn't on that default first page/filter the reopen-lookup below just found nothing and the user appeared to land on "the list" instead of "their card". `views/crm/firm_prices.py:firm_prices_page` validates `return_to` with a local `_SAFE_RETURN_RE` (same pattern as `_SAFE_NEXT_RE` in `views/admin/auth.py` — not imported, this project duplicates small private gate/validation helpers per module rather than sharing them, same reasoning as `_require_admin` in `api/*.py`) and falls back to plain `/crm/firms` only if it's missing or unsafe; `_append_query_param()` then appends `open_firm_id={{ firm.id }}` onto whatever that safe URL is (preserving any existing query string, but first **stripping out any pre-existing `open_firm_id` key** from `return_to` itself — caught in review: without this, an attacker-crafted or manually-bookmarked `return_to` already containing its own `open_firm_id` would win over the real one, since `URLSearchParams.get()` on the JS side only reads the first occurrence of a repeated key) to build `close_url`, which the template renders as the "✕" link's `href`. On the list page, `js/firms.js` picks up `open_firm_id` from the query string on load, finds the matching `.firm-name-link[data-id="..."]`, strips `open_firm_id` from the URL via `history.replaceState` **before** calling `openCardModal()` on it (ordering matters: doing it after would let the just-reopened card's own "Прайсы" link capture a `return_to` that still had a stale `open_firm_id` baked into it) — so the user lands back on the exact original page/filter with the same firm's card reopened. If that firm genuinely isn't present there (e.g. someone else's concurrent edit moved it out of the filter), the lookup silently finds nothing and the plain list is shown — no error, just a graceful fallback.

**MCP bridge for Claude, mounted at the app root**: `api/mcp_server.py` mounts a small [MCP](https://modelcontextprotocol.io) (Model Context Protocol) server directly on the same `main.py` FastAPI app via `app.mount("/", infosys_mcp.streamable_http_app())` — a plain ASGI mount, like `/CSS`/`/js`, not an `include_router()`, so it doesn't show up in `/docs`/`/redoc`. This exists because **Claude cannot call arbitrary REST endpoints** — unlike, say, Custom GPT Actions consuming an OpenAPI schema directly, Claude only speaks MCP, so a translation layer between MCP tool calls and this app's existing business logic is required. Lives in `api/`, not `core/`, despite not using `APIRouter` — it imports from `api/plus.py` (reusing that endpoint's logic directly), and `core/` by this project's convention never imports from `api/` (dependency direction is always `api/views/routers → core`, never reversed); `core/mcp_oauth.py` (see below) stays in `core/` since it has no such dependency.

**Mounted at `/` (root), not under a prefix like `/infosys_mcp`** — this was the first design, and it broke in live testing: OAuth discovery (`/.well-known/oauth-authorization-server`, RFC 8414) and dynamic client registration (`/register`, RFC 7591) are conventionally looked up at the *origin root* by real clients, not under whatever path the resource happens to live at; when this bridge was still nested under `/infosys_mcp`, connecting Claude through an ngrok tunnel produced real `404`s on `GET /.well-known/oauth-authorization-server` and `POST /register` hitting the bare domain root, confirming the mismatch empirically (not just theoretically). Moving the mount to `/` fixed it — the MCP resource itself is now at `{MCP_PUBLIC_BASE_URL}/mcp` (not `/infosys_mcp/mcp`), and `/register`, `/authorize`, `/token`, `/revoke`, `/oauth_login`, `/.well-known/oauth-authorization-server`, `/.well-known/oauth-protected-resource/mcp` all live at the root too. **This mount must stay the LAST route registered in `main.py`** (after every `include_router`/other `app.mount` call, right before `add_exception_handler`) — a `Mount("/", ...)` matches any path as a prefix, so registering it earlier would swallow every other request in the app (`/`, `/admin`, `/crm`, static files, all of it) before any real page route got a chance to match; Starlette tries routes in registration order, so "last" is what makes it a fallback rather than a black hole. Because there's no shared path prefix for these routes anymore, `middlewares/no_cache.py`'s `NO_CACHE_PATH_PREFIXES` lists each one individually (`/mcp`, `/oauth_login`, `/authorize`, `/token`, `/register`, `/revoke`, `/.well-known/oauth`) instead of one prefix.

The MCP Python SDK's `mcp.server.fastmcp.FastMCP` needs its `session_manager.run()` context manager active for the whole app lifetime for the streamable-HTTP transport to work — `main.py` didn't have a `lifespan=` before this, so one was added (`asynccontextmanager` wrapping `infosys_mcp.session_manager.run()`) purely to host this; if `main.py` ever needs other startup/shutdown logic, add it to this same `lifespan` function rather than reintroducing the deprecated `@app.on_event`.

**Authentication is a real OAuth 2.1 authorization server (Authorization Code + PKCE), not a shared secret** — this was a deliberate pivot after a first attempt (a static `X-Infosys-Api-Key` header checked against one hardcoded `MCP_SERVICE_USER_EMAIL`, in a now-deleted `core/mcp_auth.py`) turned out not to work: Claude's remote-connector UI (claude.ai and Claude Desktop alike, for any connector not on the same machine reachable via a local stdio process) doesn't have a field for an arbitrary auth header — it either treats the server as fully open, or drives a real OAuth flow discovered via `/.well-known/oauth-authorization-server`, optionally registering itself as a client via RFC 7591 dynamic client registration (`POST /register`). The user explicitly needed this to work from other computers (not just the machine running the dev server) and eventually from a cloud deployment, which ruled out the simpler "local stdio MCP server launched directly by Claude Desktop" alternative (no network/auth question at all in that model, since Claude launches the process itself) — see chat history if this tradeoff needs revisiting.

`core/mcp_oauth.py:InfosysOAuthProvider` implements the `mcp` SDK's `OAuthAuthorizationServerProvider` protocol (`get_client`/`register_client`, `authorize`, `load_authorization_code`/`exchange_authorization_code`, `load_refresh_token`/`exchange_refresh_token`, `load_access_token`, `revoke_token`) — passing an instance of it as `auth_server_provider=` to `FastMCP(...)` (in `api/mcp_server.py`) makes the SDK auto-wire `/{.well-known/oauth-authorization-server,authorize,token,register,revoke}` (via `mcp.server.auth.routes.create_auth_routes`) and wrap the `/mcp` route in bearer-token-checking middleware — none of this HTTP plumbing is hand-written, only the provider's storage/business logic is. **Storage is in-memory only** (plain `dict`s for registered clients, pending authorizations, single-use authorization codes, access/refresh tokens) — a deliberate demo-scale choice, not durable across process restarts or multiple workers; revisit (move into `data/infosys.db` via new SQLModel tables) if that becomes a real problem, e.g. once this runs behind a load balancer with multiple worker processes. `revoke_token()` maintains explicit cross-reference dicts (`_access_to_refresh`/`_refresh_to_access`) between an access token and the refresh token issued alongside it — access and refresh tokens are otherwise two independent random strings with no inherent link, so without this bookkeeping, revoking one silently left the other fully valid (a real bug caught in review and fixed; verified live by revoking an access token, confirming the same access token then fails, and confirming its paired refresh token *also* now fails at `/token`). Refresh tokens carry their own `expires_at` (`REFRESH_TOKEN_TTL_SECONDS = 30 days`) — an earlier version left this `None` (meaning never-expiring, since the SDK's own expiry check is skipped when `expires_at` is `None`), also caught in review and fixed.

**The key design decision**: authorization happens as a REAL InfoSys user, not one shared fixed service account. `OAuthAuthorizationServerProvider.authorize()`'s contract is normally used to redirect to a *third-party* OAuth provider and return here later — this project doesn't do that (InfoSys itself is the identity provider), so `authorize()` instead stores the pending `AuthorizationParams` keyed by a random `request_id` and returns a URL to this app's *own* `/oauth_login` route (a `@mcp.custom_route`, which the SDK deliberately exempts from the bearer-token requirement since it's part of the auth flow itself — see the docstring on `FastMCP.custom_route`). That route reuses the **existing** login machinery unchanged: `core.auth.resolve_authenticated_access` on the ordinary session cookie; if not logged in, it redirects to `/admin/login?next=/oauth_login?req=...` — the exact same shared login page and `next`-redirect mechanism documented under "Authentication for any-logged-in-user pages" above, so a user logs in with their normal InfoSys email/password, nothing MCP-specific. Once authenticated, `_PendingAuthorization.locked_to_email` is set to whichever user's session first viewed/acted on that specific `request_id` (checked on every subsequent visit, GET or POST) — this closes an OAuth login/consent-CSRF gap caught in review: without it, an attacker could start their own authorization flow, then trick a victim who already has an active InfoSys session into visiting/submitting that same `req_id`'s consent page, silently granting the *attacker's* client access under the *victim's* identity; with the lock, a mismatched email is rejected with `403` (verified live: a second user attempting to approve a `req_id` already opened by the first gets exactly this). It then renders `templates/mcp_oauth_consent.html` (a plain confirm/deny form naming the requesting client and the logged-in user's own email) — approving calls `InfosysOAuthProvider.complete_authorization(request_id, current_user.email)`, which issues a single-use authorization code with `AuthorizationCode.subject = current_user.email` and redirects back to the client's real `redirect_uri`; denying calls `deny_authorization()`, redirecting with `error=access_denied` per RFC 6749 §4.1.2.1. The PKCE `code_verifier`/`code_challenge` check itself, and the authorization code's single-use/expiry/redirect-uri-match enforcement, all happen inside the `mcp` SDK's own `TokenHandler` — `core/mcp_oauth.py` doesn't re-implement that, only issues/stores the tokens.

Every tool's identity resolution is the same one-liner: `mcp.server.auth.middleware.auth_context.get_access_token()` (an SDK-managed contextvar, populated by its `AuthContextMiddleware` from the request's `Authorization: Bearer <token>` header before the tool runs) gives the current `AccessToken`, whose `.subject` (the email set at authorization time above) is turned back into a real `User` row by `core.mcp_oauth.resolve_user_by_subject` (also rejects a since-deactivated `isactive=False` user, same defensive check as `resolve_authenticated_access`) — every MCP tool call therefore runs with that specific person's actual roles (e.g. `user_has_role(session, user.id, "admin")` in the `whoami` tool checks *their* real admin status, not a fixed account's), and there's no way for a caller to act as anyone else. Each tool opens its own short-lived `Session(engine)` directly (MCP tools aren't FastAPI routes, so `Depends(get_session)` isn't available) via the shared `_current_session_and_user()` helper, closing it in a `finally` block. Business logic is **reused, not duplicated, from the equivalent HTTP endpoint** wherever one already exists — `search_firms_tool` runs the identical sequence as `api/firm.py:search()` (resolve `City`/`FirmType` by name, call `core.firm_search.search_firms`, case-insensitive dedup against existing `Firm.name` rows, insert with `user_id` = the resolved user), and `list_my_tasks` mirrors `views/crm/tasks.py:tasks_page()`'s two queries (aliased `User` join for the "other side" of the task, joined to `TaskStatus`). Calling the real FastAPI route functions directly wasn't an option — they read `request.session["user_id"]`, which doesn't exist for an MCP tool call authenticated via bearer token — so instead the same SQLModel queries/helpers are re-expressed against the resolved user.

`FastMCP(...)` is also constructed with `transport_security=TransportSecuritySettings(enable_dns_rebinding_protection=False)` — the SDK auto-enables a localhost-oriented DNS-rebinding/Host-header check whenever `host="127.0.0.1"` (the default, unchanged — the process itself still only binds locally; only a separate tunnel/reverse-proxy in front, e.g. ngrok today or a real cloud load balancer later, exposes it externally), which would otherwise reject every legitimate request arriving with a non-localhost `Host` header (an ngrok subdomain, or a future production domain). Disabled deliberately with a comment explaining that Host validation in that case is the tunnel/proxy's job, not this library's. Relatedly, `core.auth.SESSION_COOKIE_SECURE` (env var, default `false`) controls whether `SessionMiddleware`'s `https_only` is set — the session cookie backing `/admin/login` and `/oauth_login` now needs to work correctly whether the app is reached over plain `http://127.0.0.1:8000` (local dev — `Secure` cookies wouldn't even be sent by the browser here) or a real HTTPS tunnel/deployment (where `Secure` should be on) — set `SESSION_COOKIE_SECURE=true` in `.env` only in the latter case.

**`MCP_PUBLIC_BASE_URL`** (env var, `.env`/`.env.example`, read once at `api/mcp_server.py` import time) is the externally-reachable base URL Claude will actually use — `http://127.0.0.1:8000` for pure local testing, or the current `https://<subdomain>.ngrok-free.app` while tunneling, or eventually a real cloud domain — used to build both `issuer_url` (`{base}`, the bare origin) and `resource_server_url` (`{base}/mcp`) in the `AuthSettings` passed to `FastMCP`. **Operationally important**: a free ngrok tunnel gets a new random subdomain every time it's restarted, so `MCP_PUBLIC_BASE_URL` needs updating (and the server restarting, and Claude's connector reconnecting/re-registering — the in-memory client/token stores don't survive a server restart either) each time; a paid ngrok reserved domain or a real deployment removes this friction.

**Deliberately small first-pass tool set** (chosen with the user before implementation, not the full `api/` surface): `whoami` (returns the resolved identity + admin flag — sanity-check that the OAuth flow authenticated the expected account), `add_numbers` (thin wrapper over `POST /api/plus`, exists purely to prove the MCP mount works end-to-end with zero DB complexity), `search_firms_tool`/`list_firms_tool`/`list_cities_and_types` (mirrors `/crm/firm_finder` + `/crm/firms`), and `list_my_tasks` (mirrors `/crm/tasks`, `role="assignee"`/`"author"`). No admin-gated resource (`task_status`/`city`/`firm_type`/`unit`/`constants`/`bug`/`notification` CRUD) is exposed yet — if one is added later, gate it the same way `whoami` does (check `user_has_role(session, user.id, "admin")` on the resolved user and raise if absent). `list_firms_tool`'s `limit` is capped at `MAX_LIST_FIRMS_LIMIT = 50` (clamped server-side, not just documented) — unlike `/crm/firms`'s real pagination, this is a first-pass blunt cap rather than proper `page`/`PAGE_SIZE` paging, acceptable for a small MCP tool result but revisit if the `firm` table grows large enough that 50 stops being enough context for a typical query.

**AI task queue (`list_ai_tasks`/`submit_firm_price_items`/`complete_ai_task`)**: a mechanism letting an external Claude Code session — connected through this same MCP bridge, but running as a long-lived process on a machine the user controls (their own PC, kept open/logged in under their own Claude subscription) rather than this app's backend — pick up and execute AI-heavy work using its own built-in tools (web search/fetch) instead of the metered `anthropic` SDK calls in `core/firm_search.py`/`core/firm_price_download.py`. This was a deliberate architecture choice after discussion with the user: running such a worker *on* FastAPI Cloud itself isn't viable (no Node/CLI runtime, ephemeral disk — this project already hit that exact ephemeral-disk issue once, see `db/migrate.py` above — and OAuth login there would need a browser anyway), so the worker lives externally and reaches the cloud-hosted `/mcp` endpoint the same way Claude Desktop already does.

No new tables — deliberately reuses `Task` (the existing queue: a human creates a `Task` and assigns it to a designated "AI" `User` account) and `Constant` (`/admin/constants`, no code needed): a row named `AI_USER_ID` whose `value` is that `User`'s id (as a plain string, per `Constant`'s existing string-only value column) is the *only* thing tying the queue to a specific account — `api/mcp_server.py:_get_ai_user_id(session)` reads and validates it (missing constant / non-integer value / dangling user id all raise a clear `ValueError`, not a raw exception) and is called fresh on every tool invocation, never cached. Since a `Task` has no FK to `Firm`, which firm a price-download task is about is conveyed only in freeform `title`/`description` text — the calling Claude Code session is expected to resolve it itself via `list_firms_tool`/`list_cities_and_types` (this is exactly the kind of fuzzy resolution an LLM is good at, so no schema change was added for it).

- `list_ai_tasks()` returns not-yet-completed `Task` rows where `assignee_id == AI_USER_ID` — **deliberately not scoped to whoever the MCP caller is actually authenticated as** (unlike `list_my_tasks`, which always looks at the caller's own id), by explicit user decision: any authenticated MCP caller can see/act on the AI's queue, so a human doesn't need to separately log the worker in as a dedicated "robot" InfoSys account — they can just use their own normal login for the PC-side Claude Code connector. Same "any authenticated user" openness precedent as `firm_comment`/`firm_event` elsewhere in this project.
- `submit_firm_price_items(firm_id, items, note=None)` is the write-back half for price downloads — it does **not** call `core/firm_price_download.py` (that would defeat the purpose, re-introducing the paid API call this whole mechanism exists to avoid); it expects `items` already extracted by the calling Claude Code session itself, runs them through the existing `_prepare_price_items()` normalizer, and persists via a newly-extracted shared helper, `api/firm.py:_persist_price_items(session, firm, items, rem)` — the `FirmPrice`/`FirmGoods`/`FirmPriceBody`-writing tail that used to be inline in `download_price()` (the HTTP route backing the "Скачать прайс" button), pulled out specifically so both callers share one dedup/unit-resolution/`IntegrityError`-backstop implementation rather than duplicating it. `_persist_price_items` raises plain `ValueError`/`RuntimeError` (transport-agnostic) — `download_price()` translates those back into the same `HTTPException` status codes it always returned (422/500), while the MCP tool just lets them surface as a tool error, same as every other tool in this file. `items` (a raw `list[dict]`, no Pydantic model — MCP tool parameters aren't FastAPI request bodies) is explicitly validated by hand before use (non-empty list, each entry a dict with a non-empty string `name`, capped at `MAX_SUBMIT_PRICE_ITEMS = 200`) — caught in code review: without this, a malformed call (e.g. a missing `"name"` key) fell through to `_prepare_price_items()`'s unguarded `item["name"]` and surfaced as a bare `KeyError` instead of a clear message, inconsistent with every other validation failure in this file.
- `complete_ai_task(task_id, status=None)` sets `completed=True` and `date_finished` — a **deliberate, explicitly-confirmed exception** to this project's otherwise-firm rule that only a task's *author* may close it (see "Tasks" above and `api/task.py`): scoped narrowly to tasks where `assignee_id == AI_USER_ID` only (re-checked via `_get_ai_user_id` every call), so the AI can fully self-close its own queue items without a human confirmation step, but this tool has no effect on any other task. Optionally also moves `status_id` (by exact `TaskStatus.name` match) in the same call, folding what a human would do as two separate actions (`PATCH .../status` then `PATCH .../complete`) into one.

Verified live end-to-end with a real HTTP client walking the entire flow (not just unit-tested), twice — once for the initial nested-under-`/infosys_mcp` design, and again after moving the mount to root: dynamic client registration at `/register`, `GET /authorize` correctly redirecting to `/oauth_login`, that route correctly redirecting to `/admin/login` with the right `next` when not logged in, a real login with a temporary test account landing back on the consent page (correctly naming both the requesting client and the logged-in user's email), approving redirecting to the client's `redirect_uri` with a real `code`+`state`, exchanging that code at `/token` for an access+refresh token pair, **replaying the same already-used code correctly rejected** as `invalid_grant` (single-use enforced), calling a tool over `streamable_http_client` with the issued Bearer token and getting back the correctly-resolved identity, **an invalid Bearer token correctly rejected with 401**, a `refresh_token` grant correctly rotating to a new access token, the **deny path** correctly redirecting with `error=access_denied` while preserving `state`, **revoking an access token via `/revoke` correctly killing its paired refresh token too**, and **a second user attempting to approve a `req_id` already claimed by a first user correctly rejected with 403**. Also confirmed the un-authenticated `GET /mcp` returns `401` with a `WWW-Authenticate: Bearer ... resource_metadata="{base}/.well-known/oauth-protected-resource/mcp"` header pointing at a URL that itself correctly resolves, and that ordinary page routes (`/`, `/admin`, `/docs`, `/CSS/*`) still work unaffected by the root-level catch-all mount. `search_firms_tool` itself was deliberately **not** exercised live end-to-end (it would spend real Anthropic API credit the same way `/crm/firm_finder` does) — its logic was verified by direct code comparison against `api/firm.py:search()`, which it mirrors line-for-line. Every temporary test user created across these verification rounds was deleted afterward — `data/infosys.db` carries no leftover test data from any of it.

To connect Claude itself to this bridge as a remote/custom MCP connector, point it at `{MCP_PUBLIC_BASE_URL}/mcp` — no client ID/secret/API key needs to be entered by hand; Claude discovers the OAuth metadata itself, registers a client, and drives the user through the ordinary InfoSys login + consent page in a browser popup/tab. Exact steps depend on the installed Claude Desktop/claude.ai version's connector UI, not verified as part of this change.

**Partner application questionnaire (`/anketa`)**: the **first fully unauthenticated, data-writing page in the whole project** — every other mutating endpoint requires at least `resolve_authenticated_access`, but this one is meant to be sent as a plain link to a prospective partner (designer, bureau, installer, shop, distributor, ...) who has no InfoSys account. First step toward the AI-driven partner qualification/verification agent sketched out in `anketa.docx` (a design brainstorm, not yet implemented) — for now this is just the data-collection form + an admin review list, no scoring/verification logic yet.

`models/partner_application.py` defines `PartnerApplication` (explicit `__tablename__ = "partner_application"`, same class-name-lowercasing gotcha as `TaskStatus`/`FirmType`): `id`, indexed `created` (default-now, `server_default=sa.text('(CURRENT_TIMESTAMP)')` — same cross-dialect pattern as `firm_event.created`), required `full_name`/`phone`, optional `email`, indexed **required** `claimed_type_id` — **reuses the existing `firm_type.id` lookup table** (магазин дверей/дизайн студия/установщик дверей/...) instead of a separate classifier, per explicit user feedback that the concept already exists; not nullable, no `ondelete` (see the `api/firm_type.py:delete_firm_type` gotcha below), optional `company_name`/`company_website`/`activity_type`, indexed optional `city_id` (FK → `city.id`, **nullable and deliberately never auto-created**: see below), optional `city_other` (free-text fallback), optional `has_physical_office` (nullable bool — `None` means "not specified/unknown", a genuine tri-state, not a default-`False` boolean), optional `projects_description`/`projects_count` (text, not int — "не знаю"/"10-20" are valid answers, same reasoning as `Task`'s free-text fields) `/customer_segment`, `wants_discount`/`wants_sample` (bool, Python default `False` **and** `server_default="0"`, same split as `Firm.rating` elsewhere), optional `comment`, indexed **required** `status_id` (FK → the new `application_states.id`, see below — never set by the public form, always server-assigned to the "новая" row on insert), and indexed optional `client_ip`/`user_agent` (populated from the request, same fallback/truncation convention as `core.auth.record_login_attempt` for `login_info` — useful for spotting spam/abuse on this, the one fully unauthenticated write endpoint in the project).

`models/application_state.py` defines `ApplicationState` (explicit `__tablename__ = "application_states"` — **deliberately plural**, an explicit override requested directly, same precedent as `Constant` → `constants`): `id` + unique-indexed `name`, identical shape to `TaskStatus`/`City`/`Role`. Seeded via migration (`op.bulk_insert`, same style as `unit`/`channel_type`) with exactly 5 rows: `новая`, `на рассмотрении`, `подтверждена`, `под вопросом`, `не подтверждена`. No admin CRUD page for this table yet (same deliberate deferral as the `search_*` reference tables) — `routers/anketa.py:_get_default_application_state_id()` looks up the `"новая"` row by name on every insert (never cached — if the seed row is ever missing, e.g. through a future admin delete feature, it raises a clear `HTTPException(500, ...)` rather than crashing on `None.id`) and `views/admin/partner_applications.py` joins it in for display/filtering — there is still no UI to *change* an application's `status_id` after creation, same as before this rework, just a real FK now instead of a plain string.

Adding `PartnerApplication.claimed_type_id` as the **first FK ever pointing at `firm_type.id`** reproduced the exact same class of gap already fixed once for `firm_channel`/`firm_event`, caught in code review: `api/firm_type.py:delete_firm_type` used to unconditionally `session.delete(target); session.commit()` with no in-use guard (previously safe, since nothing referenced `firm_type` at all — CLAUDE.md used to note this explicitly). Fixed the same way `task_status.py:delete_status`/`firm.py:delete_firm_channel` handle this: `delete_firm_type` now pre-checks for a referencing `PartnerApplication` and returns a friendly `400` if found, plus wraps the delete/commit in `try/except IntegrityError` as a TOCTOU backstop.

**`City` is never auto-created from this form** — a real design decision, not an oversight: `city` is a shared reference table used project-wide (firm search/filtering, the `/crm` donut charts) and has always been editable only through the admin-gated `/admin/city` AJAX endpoints (see the "AJAX reference pages" section above). Letting a fully anonymous public submitter silently insert rows into it would be the first crack in that rule and an open spam vector. Instead, `routers/anketa.py:submit_anketa` only ever accepts an EXISTING `city_id` (validated via `session.get(City, ...)`) — a submitted id that's non-numeric, out of range, or doesn't match a real row is silently ignored (falls through to requiring `city_other` instead), never used to construct a `City` row. An admin reviewing an application can add the city to the real `City` table by hand via `/admin/city` if they judge it worth it.

`views/anketa.py:anketa_page` (`GET /anketa`, registered as an ordinary `PageRoute`) does no auth check at all and supplies a `_BLANK_FIELDS` dict of empty defaults for every form field, so the Jinja template never sees an undefined variable on a fresh visit. `routers/anketa.py:submit_anketa` (`POST /anketa/submit`, a separate router registered in `main.py` — GET/POST split the same way `/admin` setup/login is, since `PAGE_ROUTES` is GET-only by convention) validates `full_name`/`phone`/`claimed_type_id` as required (the latter via a shared `_parse_bounded_id()` helper — also used for `city_id` — that caps the parsed value at `MAX_QUERY_INT` before ever calling `session.get(...)`, since a raw `int()` on a fully unauthenticated field has no upper bound and previously crashed with an unhandled `OverflowError`/out-of-range DB error on a crafted oversized id; caught in code review, fixed here for both fields), requires either a valid `city_id` or a non-empty `city_other`, and enforces a **per-field max length** (`_LENGTH_LIMITS`, e.g. 200 chars for `full_name`, 5000 for `comment`) — the only place in the project besides `BugReportIn.title` that caps free-text length, and here it actually matters since there's no auth barrier at all guarding against a scripted flood of oversized submissions. On any validation failure, the handler re-renders `anketa.html` directly (not a redirect) with the error and everything the visitor already typed, status `400` — same "GET shows form / POST re-renders with error on failure" shape as `views/admin/usermgt.py:create_user`. On success it creates the row and does a 303 redirect to `/anketa?submitted=1`, which `anketa_page` reads to show a thank-you message instead of the form. No CSRF token is used here (unlike `usermgt`'s `edit_user`/`change_password`) — deliberately, since CSRF protects an *existing authenticated session* from being abused by a forged cross-site request, and this form has no session to forge in the first place.

Caught in code review: the `city_id` parser originally only guarded against a non-numeric string (`except ValueError`) — since Python's `int()` has arbitrary precision, a crafted `city_id` like `"99999999999999999999999999"` parsed successfully and was then handed to `session.get(City, ...)`, which raised an unhandled `OverflowError` on SQLite (or an out-of-range error on Postgres) — a real unauthenticated-500 bug. Fixed by bounding the parsed value against the same `MAX_QUERY_INT` cap `views/crm/firms.py`/`views/admin/partner_applications.py` already use for query-string ids, before ever calling `session.get`.

**Admin review (`/admin/partner_applications`)**: admin-gated (`resolve_admin_access`), a filter+pagination list mirroring `views/crm/firms.py`'s exact shape (same `_escape_like`/`_parse_positive_int`/windowed-pagination pattern, `PAGE_SIZE = 10`) — filterable by `claimed_status`, `city_id`, and a `q` substring search across `full_name`/`company_name`. Clicking the company name (falling back to the applicant's own name if no company was given) opens the full anketa — reuses the `<template>`-per-row-cloned-into-a-shared-modal technique from `usermgt.html` (`templates/admin/partner_applications.html` + `js/partner_applications.js`) rather than the AJAX-inline-edit pattern, since this is **view-only** for now (no edit/approve UI yet — that's deferred, `review_status` exists in the model precisely so adding it later doesn't need a migration). The city column/detail falls back to `city_other` when `city_id` is null (LEFT JOIN to `City`, not an inner join, so nullable-city rows aren't silently dropped from the list — same reasoning as `login_info_page`'s left join to `User`).

## Tests

`tests/test_api_plus.py` uses `fastapi.testclient.TestClient` against the real `main.app` (no fixtures/mocking) to test the `/api/plus` endpoint directly. Follow this pattern (import `app` from `main`, hit routes with `TestClient`) for new API tests.

`pytest.ini` (`pythonpath = .`) makes `.venv\Scripts\pytest.exe` importable from the repo root — without it, pytest's default "prepend" import mode only puts `tests/`'s own rootpath on `sys.path`, not the repo root, so `from main import app` in a test module fails with `ModuleNotFoundError: No module named 'main'` when invoked via that console-script entry point specifically (`python -m pytest` was never affected, since `-m` already adds the cwd itself).

## Workflow rules

Bugs found in existing project code during an audit-style task (code review, writing tests for pre-existing code, running the test suite) must be delegated to the bug-fixer subagent — announce the finding to the user first, then delegate. Bugs the main agent notices in code it is actively drafting within the same task do not require delegation — fix them inline as normal iterative work. Subagents cannot invoke each other or contact the user directly; only the main agent can decide to delegate.

## Project subagents

- **code-reviewer** (`Read, Grep, Glob` — read-only). Reviews code for bugs, security issues, and project convention violations (correct `data/infosys.db` usage, `PAGE_ROUTES`/`render_page()` registration for new pages, new SQLModel models imported in `alembic/env.py`). Cannot edit anything, only reports findings. Invoke proactively after any code change.
- **test-writer** (`Read, Write, Edit, Bash`). Writes pytest tests following the `TestClient`-against-real-`main.app` pattern from `tests/test_api_plus.py`, no mocking. If existing code's behavior looks wrong while writing a test, it asserts the correct behavior, lets the test fail, and reports the discrepancy instead of fixing the code. Invoke proactively for new or existing functionality that needs test coverage.
- **test-runner** (`Bash` only — no source access). Runs `.venv\Scripts\pytest.exe` (with `--cov` when relevant) and reports a compact pass/fail summary with one-line failure reasons, no tracebacks. Suggests delegating to another agent when a failure needs investigation rather than digging in itself. Invoke proactively to run the suite and get a quick status.
- **bug-fixer** (`Read, Write, Edit, Bash`). Applies a fix for one already-identified bug (from code review, test-writer, or test-runner output) — no drive-by refactors or unrelated fixes. Verifies the fix via pytest or a manual curl check against a locally started dev server, and reports with the phrase "Fix applied by bug-fixer" plus a real diff. Invoke only for bugs already identified in existing code, not for fresh feature work or for fixing code drafted earlier in the same task.
- **db-migrator** (`Read, Write, Edit, Bash`). Handles the Alembic workflow after a model change: registers new model imports in `alembic/env.py`, runs `alembic revision --autogenerate`, fixes known gotchas (missing `import sqlmodel`, accidental `ON DELETE CASCADE`), runs `alembic upgrade head`, and verifies against the real `data/infosys.db` including a live FK-enforcement check when foreign keys are involved. Forward-only — never runs `alembic downgrade` or edits an already-applied migration. Invoke proactively after adding or changing a SQLModel model.
